# 前端框架入门

::: 提示 前言
你已经学会了HTML、CSS和JavaScript的基础知识，现在可以构建简单的网页了。但随着网页功能变得越来越复杂，你可能会发现，编写原始JavaScript变得难以维护——改变一件事需要处理很多地方，协作往往会导致冲突。

这就是为什么我们需要前端框架——它们让代码更有条理、更易维护，开发更高效。在氛围编码中，AI为你编写大部分代码。但你至少应该能阅读不同框架的代码风格，了解它们的优缺点，这样AI才能帮助你选择最合适的技术栈。

到本文结尾，你将能够：
- 理解前端技术为何不断演进
- 了解Vue、React、Svelte和Angular的特性
- 理解“数据驱动”和“基于组件”开发等核心概念
- 为你的项目选择合适的框架

## 1.关注前端演进的动机

::: 提示 🤔 核心问题
**为什么网页变得越来越复杂？为什么前端技术不断发展？** 这个问题将引导你从简单网页到现代网页的技术历程。
:::

### 1.1 从“数字海报”到“桌面应用”

想想你在街上看到的一张**海报**：

- ✅ 有内容（文本、图片）
- ✅ 有设计（颜色、布局）
- ❌ 但如果你跟它说话，它不会回应
- ❌ 如果你在某处轻敲，什么都不会发生

**最早的网页**就像这些“数字海报”一样：仅限浏览，不可更改，内容固定。

**现代网页**完全不同。它们就像**桌面应用程序**（VS Code，Figma）：

- ✅ 你可以编辑文档、绘画、玩游戏
- ✅ 它们会实时响应你的每一个动作
- ✅ 他们甚至可以离线工作

**这一转型的核心原因：网页功能日益复杂，需要更高效的技术和开发方法。**

### 1.2 现实生活中的类比：盖房子

前端技术的发展就像房屋建设的演变：

|时代 |🏠房屋类比 |实际特征 |优缺点 |
|------|-----------|---------|--------|
|**2000年代****张贴海报** |静态网页——只需写HTML就行 |✅简单无❌互动 |
|**2010年代** |**雇工进行手工翻新** |jQuery时代——手动操作每个元素 |✅交互❌式代码混乱，难以维护|
|**2020年代** |**用乐高积木组装** |Vue/React时代——基于组件的开发 |✅高效且易于❌维护的学习曲线 |

::: 提示 💡 你能从这张表中看到什么？

**阶段 1 → 阶段 2**：从“不能动”到“能动”。这是一个质的飞跃——网页变得可以交互，但代价是代码混乱。

**阶段 2 → 阶段 3**：从“可用”到“令人愉快”。基于组件的开发使代码像积木一样可重用，极大地提高了开发效率。

**核心见解**：技术进化并不是“为了新而新”——它旨在解决前一阶段的痛点。

## 2. 阶段 1：静态网页与“图像切片”（2000 年代）

::: 提示 🤔 核心问题
**最早的网页是怎样的？为什么那时不需要框架？** 理解这一阶段的局限性有助于你明白为什么后来的发展是必要的。
:::

<前端演示进化 />

### 2.1 这一时代的概况是怎样的

**开发方法**：

- 编写一些 HTML 文件
- 嵌入一些 CSS 和 JavaScript
- 直接将文件拖入浏览器查看结果
- 将文件夹上传到服务器以部署

**特点**：

- ✅ **优点**：简单直接，无需学习成本，编写并运行
- ❌ **缺点**：没有复杂的交互，代码随着增长变得杂乱

::: 详情 查看那个时代的项目结构

```
project/
├── index.html
├── login.html
├── css/
│   ├── bootstrap.css
│   └── custom.css
├── js/
│   ├── jquery.js
│   └── app.js
└── images/
```

**遇到的问题**：

1. **全局变量污染**：所有变量都存在于全局命名空间中，容易互相覆盖  
2. **依赖管理混乱**：JavaScript 文件必须按正确顺序加载，否则会出错  
3. **代码难以复用**：要复用功能，只能复制粘贴  
:::

### 2.2 “切片图片”概览

你可能听过“切片图片”这个术语。这是早期前端工作的主要任务：

**什么是切片图片？**

设计师在 Photoshop 中创建页面布局 → 前端开发者将设计切成小图 → 用 HTML 将这些小图拼接成页面  

**为什么这么慢？**

网页上的每个小图都需要浏览器发起单独的 **网络请求**。请求越多，加载越慢。

## 3. 第二阶段：jQuery 时代 — “手工劳动”（2010 年代）

::: tip 🤔 核心问题
**为什么需要 jQuery？它解决了什么问题，又带来了哪些新问题？** 了解 jQuery 的局限性能帮助你更好地理解 Vue/React 的价值。
:::

### 3.1 需要 jQuery 的动机

随着网页变得越来越复杂，原生 JavaScript 的问题显现出来：

- ❌ **API 冗长**：简单操作也需要写大量代码  
- ❌ **浏览器兼容性**：不同浏览器有不同 API，需要写大量兼容代码  
- ❌ **选择器能力弱**：查找元素很麻烦  

**jQuery** 应运而生。它让 JavaScript 更简单：

```javascript
// Vanilla JavaScript (verbose)
const element = document.getElementById('title')

// jQuery (concise)
const element = $('#title')
```

### 3.2 jQuery 的方法：手动修改页面

jQuery的核心方法是**必然**：你告诉浏览器“怎么做”。

```javascript
// Find the title element
$('#title').text('New Title')

// Find the button and disable it
$('#submit-btn').attr('disabled', true)

// Find the list and add an item
$('ul').append('<li>New Item</li>')
```

**问题**：你需要记住页面上的每一个元素，并且每当数据发生变化时，你必须手动更新所有相关的元素。

👇 **自己试试**：比较 jQuery 和数据驱动的方法

<JQueryVsStateDemo />

::: warning ⚠️ jQuery 的痛点

想象一下你正在构建一个购物车：

```javascript
// User clicks "Add to Cart"
function addToCart() {
  cartCount++ // Data changes

  // You have to manually update every related spot
  $('#cart-count').text(cartCount) // Top-right badge
  $('#cart-page-count').text(cartCount) // Cart page
  $('#checkout-price').text(calculatePrice()) // Checkout button

  // If you miss one spot, the page becomes inconsistent!
}
```

**这是“人工劳动”的代价**：容易出错且难以维护。
:::

### 3.3 移动崛起：响应式设计出现

这一阶段的另一个重大变化：**手机和平板成为主流**。

网页必须适应不同的屏幕。这就需要**响应式布局**：相同的 HTML/CSS 根据屏幕宽度自动调整布局。

**响应式布局的核心：媒体查询**

```css
/* Desktop screens (wider than 640px) */
@media (min-width: 640px) {
  .container {
    display: flex;
  }
}

/* Mobile screens (narrower than 640px) */
@media (max-width: 640px) {
  .container {
    display: block;
  }
}
```

想象在不同的房间里看同一张照片：

- 在**大客厅**（桌面屏幕）中，照片可以显示得更大，还有空间摆放其他装饰

**响应式布局**就是那个“智能相框”，能根据房间大小自动调整显示方式。

## 4. 第三阶段：从“手工操作”到“数据驱动”（Vue/React）

::: tip 🤔 核心问题
**为什么我们需要 Vue/React？它们与 jQuery 的本质区别是什么？** 理解“声明式”和“数据驱动”是掌握现代前端框架的关键。
:::

### 4.1 需要新框架的动机

jQuery 时代的问题积累到了临界点：

- **代码随着增长变得混乱**：到处都有 DOM 操作，很难维护
- **容易出现 bug**：错过一次更新，页面就会不一致
- **协作困难**：多人编辑同一文件容易产生冲突

**Vue / React** 核心方法：**只需改变数据，页面自动更新**。

### 4.2 Vue/React 的方法：声明式 UI

**jQuery（命令式）**:

```javascript
// You tell the browser every step to take
$('#title').text('New Title')
$('#title').css('color', 'red')
$('#title').show()
```

**Vue（声明式）**：

```javascript
// You just tell the browser "what to display"
data() {
  return {
    title: "New Title",
    color: "red",
    visible: true
  }
}
```

<命令Vs声明式演示 />

::: 提示 💡 命令式与声明式

这就像在画一幅画：

- **祈祷语**：你告诉画家“拿起画笔，蘸上红色颜料，在坐标（10， 10）画一个圆”。
- **声明语句**：你递给画家一张照片，说“像这样画”

Vue/React是“声明式”的：你描述“页面应该长什么样”，框架负责“如何绘制”页面。
:::

### 4.3 基于组件的开发：构建像乐高一样的页面

**Vue / React** 最强大的功能是**基于组件的开发**：将页面拆分为独立的“构建模块”。

想象你正在用乐高积木：

- 你不需要“从零开始雕刻每个块”（从零写 HTML/CSS）
- 你只需“按照说明组装模块”（将组件组合在一起）
- 每个块是**独立的**，可以在不同集合间**重复使用**

**组件的优势**：

- **可重复使用**：编写一个“产品卡”组件并使用100次
- **封装**：组件的内部状态不影响其他组件
- **可维护性**：修改组件，所有使用该组件的地方都会更新

::: 信息 💡 识别技巧
- 参见 `<ComponentName />` → 这是一个组成部分
- 参见 `import xxx from './xxx.vue'` → 导入组件
- 参见 `props: {...}`@ → 组件接收的参数
- 参见 `emit('xxx')` → 组件向其父节点发送事件
:::

### 4.4 SPA：单页申请的诞生

**Vue / React**时代带来了另一个重大转变：**从MPA转向SPA**。

**多页申请（MPA）**：

- 点击链接→全页刷新→查看新页面
- 就像**翻书**：每翻一页，你就合上旧书，从书架上拿新的

**SPA（单页申请）**：

- 点击链接→仅内容区刷新→页面本身不会重新加载
- 比如**在同一本书中切换章节**：只擦掉旧内容，写入新内容

**SPA优势**：

- ✅ **流畅体验**：快速的页面转换
- ✅ **简易状态管理**：表单输入和滚动位置得以保留
- ❌ **初始加载可能较慢**：必须先下载JavaScript
- ❌ **SEO需要额外处理**：搜索引擎不得索引内容（需要SSR/SSG）

## 5.渲染策略：从 CSR 到 SSR/SSG

::: 提示 🤔 核心问题
**页面是在服务器生成还是在浏览器中生成？** 不同的渲染策略有不同的权衡——选择合适的策略对性能和SEO至关重要。
:::

**CSR（客户端渲染）**：

- 浏览器下载JavaScript→执行代码→生成页面
- 优点：交互流畅，服务器负载低
- 缺点：初始加载缓慢，对SEO不利

**SSR（服务器端渲染）**：

- 服务器生成 HTML，→直接发送到浏览器→浏览器显示
- 优点：快速初始加载，对SEO有利
- 缺点：服务器负载较高，实现复杂

**SSG（静态站点生成）**：

- 在构建时为所有页面生成 HTML
- 优点：极其快速，完全静态，支持CDN
- 缺点：不适合动态内容

👇 **自己试试**：比较不同渲染策略的特性

<RenderingStrategyDemo />

::: 信息 💡 如何选择？
- **内容网站**（博客、文档）：偏好SSG
- **需要SEO的动态网站**（电商、新闻）：使用SSR
- **管理仪表盘**：使用CSR
- **混合需求**：考虑与Nuxt/Next.js进行混合渲染

## 6.第四阶段：工程与构建工具（2015年代–2020年代）

::: 提示 🤔 核心问题
**为什么前端需要“工程”？构建工具到底是做什么的？** 理解工程有助于你掌握现代前端项目的工作流程。
:::

### 6.1 需要“工程”的动机

前端项目已经变得太大，无法依赖“手动包含脚本”。

**工程**意味着使用工具和标准来提高开发效率、代码更可靠、协作更顺畅。

::: 提示 💡 工程 = 从“手工艺作坊”到“现代工厂”

想象一下在家做饭和经营餐厅的区别：

- **在家做饭**：随心所欲地做饭，非常自由
- **经营餐厅**：需要标准化的食谱、标准化流程、统一的食材采购

前端开发也是一样的：

- **小项目**：随你喜欢写
- **大型项目**：需要统一的代码标准、自动化工具、标准化流程
:::

### 6.2 构建工具：Webpack → Vite。

**Webpack（传统版）：

- 工作原理：**先打包，再服务**
- 启动时：捆绑所有代码→启动开发服务器
- 问题：**慢**。项目越大，启动越慢（可能需要30秒）

**Vite**（现代）：

- 工作原理：**按需编译**
- 启动时：不捆绑，直接启动开发服务器
- 当浏览器请求文件时，实时编译
- 优势：**快速**。通常在1秒内开始

|比较 |Webpack |Vite |改进 |
|--------|---------|------|------|
|冷启动 |30秒 |<1秒 |**快30倍** |
|热装填 |3–5秒 |<100毫秒 |**快30倍** |
|配置文件 |数百行 |数十行 |**极度简化** |

::: 提示 💡 为什么Vite这么快？

**Webpack**就像**搬家时所有东西都打包好**：先打包好，然后再出发。

**Vite**就像**轻装旅行**：只带必需品，路上买你需要的东西。

在开发过程中，大多数时候你只需要修改少数文件。Vite只编译这些文件——当然它很快。
:::

## 7.主流框架的比较

::: 提示 🤔 核心问题
**Vue、React、Svelte 和 Angular 有哪些特点？如何选择合适的框架？** 理解它们的设计理念和使用场景有助于你做出明智的决策。
:::

### 7.1 四框架比较

|特征 |Vue |反应 |Svelte |角度 |
|------|-----|-------|--------|---------|
|**设计理念** |渐进框架 |界面库 |编译时框架 |完整平台 |
|**学习曲线**⭐⭐简单 |⭐⭐⭐中等 |⭐⭐简单 |⭐⭐⭐⭐陡峭 |
|**表演** |快 |快 |**极其快** |快 |
|**生态系统** |成熟 |**最成熟** |正在成长 |成熟 |
|**包裹大小** |小 |中 |**最小** |大 |
|**最佳用途** |中小型项目 |大型项目 |性能关键 |企业应用 |
|**支持者** |Evan You（独立）|Meta |社区 |谷歌 |

### 7.2 Vue：渐进框架

**核心理念**：逐步采用——仅使用部分或全部套件

```vue
<template>
  <div>{{ message }}</div>
</template>

<script>
export default {
  data() {
    return {
      message: 'Hello Vue'
    }
  }
}
</script>
```

**优点**：
- ✅ 学习曲线温和，中文文档优秀
- ✅ 模板语法直观，易于理解
- ✅ 单文件组件（.vue），结构清晰
- ✅ 非常适合快速开发

**缺点**：
- ❌ 大型项目中的状态管理需要学习 Vuex/Pinia
- ❌ 灵活性略低于 React

**适合**：
- 中小型 Web 应用
- 快速原型开发
- 中文团队（文档友好）

### 7.3 React: UI 库

**核心理念**：只关注视图层；其他一切由社区解决

```jsx
function App() {
  const [message, setMessage] = useState('Hello React')
  return <div>{message}</div>
}
```

**优点**：
- ✅ 最成熟的生态系统，组件库丰富
- ✅ 灵活的 JSX 语法，表达能力强
- ✅ 出色的虚拟 DOM 性能
- ✅ 非常适合大型项目

**缺点**：
- ❌ 学习曲线较陡，需要掌握额外概念
- ❌ 需要自己选择和组合各种库
- ❌ JSX 需要编译，不能直接在浏览器中运行

**适合**：
- 大型复杂应用
- 需要丰富生态系统的项目
- 跨平台开发（React Native）

### 7.4 Svelte：编译时框架

**核心理念**：无虚拟 DOM —— 在构建时将组件编译为高效的原生代码

```svelte
<script>
  let message = 'Hello Svelte'
</script>

<div>{message}</div>
```

**优点**：
- ✅ **最佳性能**（无虚拟 DOM 运行时开销）
- ✅ 最小的包体积
- ✅ 简单直观的语法
- ✅ 内置响应式系统

**缺点**：
- ❌ 相对较小的生态系统
- ❌ 社区比 Vue/React 小
- ❌ 第三方库较少

**适合**：
- 对性能要求高的应用
- 对包体积敏感的项目
- 愿意尝试新技术的团队

### 7.5 Angular：完整平台

**核心理念**：提供一个完整的开箱即用解决方案

```typescript
@Component({
  selector: 'app-root',
  template: '<div>{{ message }}</div>'
})
export class AppComponent {
  message = 'Hello Angular'
}
```

**优点**：
- ✅ 功能齐全——路由、HTTP、表单全包
- ✅ 原生TypeScript支持
- ✅ 非常适合大型团队和项目
- ✅ 一致的代码标准

**缺点**：
- ❌ 陡峭的学习曲线
- ❌ 概念多，复杂度高
- ❌ 大束
- ❌ 不适合小型项目

**最佳用途**：
- 大型企业应用
- 要求严格标准的球队
- 已在TypeScript栈上的项目

## 8.摘要：进化的本质

前端技术演进本质上是解决两个问题：

### 8.1 效率：从手动到自动

|时代 |发展方法 |效率 |
|------|---------|------|
|**2000年代** |手写HTML/CSS/JS |⭐ |
|**2010年代**jQuery 手册 DOM 操作 |⭐⭐ |
|**2020年代**Vue/React数据驱动 |⭐⭐⭐ |
|** 现状** |基于组件的工程自动化 |⭐⭐⭐⭐⭐ |

### 8.2 比例：从个人到团队

|时代 |项目规模 |协作风格 |
|------|---------|---------|
|**2000年代**几个文件 |一个人可以维护 |
|**2010年代** |数十个文件 |小团队，容易冲突 |
|**2020年代** |数百个文件 |中型团队，需要标准 |
|**今天** |成千上万的文件 |大团队，需要完整的工程系统 |

## 词汇表

| 术语 | 英文 | 通俗解释 |
|------|------|-----------|
| **DOM** | 文档对象模型 | 将页面表示为对象树，可被 JS 读取和写入。|
| **jQuery** | — | 早期流行的 JS 库，简化了 DOM 操作。|
| **Vue/React** | — | 现代前端框架，使用数据驱动和组件化开发。|
| **组件** | Component | 可重用的 UI 单元，如按钮、卡片或导航栏。|
| **MPA** | 多页应用 | 每次导航都会重新加载整个页面。|
| **SPA** | 单页应用 | 页面只加载一次；后续导航不会刷新页面。|
| **路由** | Routing | 管理页面之间导航的规则和过程。|
| **SSR** | 服务器端渲染 | 服务器生成 HTML 并发送到浏览器。|
| **SSG** | 静态站点生成 | 页面在构建时预渲染为静态 HTML。|
| **CSR** | 客户端渲染 | 浏览器通过 JavaScript 生成页面。|
| **Webpack** | — | 传统打包工具 — 先打包，再提供服务。|
| **Vite** | — | 现代构建工具 — 按需编译，非常快速。|
| **响应式** | 响应式设计 | 自动适应不同屏幕尺寸的设计。|
| **媒体查询** | Media Query | CSS 条件语句，根据屏幕宽度应用不同样式。|
| **命令式** | Imperative | 告诉程序“如何做”。|
| **声明式** | Declarative | 告诉程序“你想要什么”。|
| **数据驱动** | Data-Driven | 只修改数据；UI 会自动更新。|
| **摇树优化** | — | 自动移除未使用的代码以减小打包体积。|
| **代码分割** | Code Splitting | 将代码拆分为更小的块，按需加载。|
