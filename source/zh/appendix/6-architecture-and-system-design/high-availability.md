# 高可用性与灾难恢复原则

::: tip 介绍
**一分钟的停机可能意味着数十万的损失。** 高可用性（HA）指系统在硬件故障、软件缺陷、网络问题及其他异常情况下仍能持续提供服务的能力。灾难恢复（DR）是指在发生大规模灾难时能够恢复服务的能力。
:::

## 1. 可用性指标：“几个九”是什么意思

可用性通常以“几个九”衡量，计算公式为：

**可用性 = 正常运行时间 / 总时间 × 100%**

例如，如果一个系统在一个月（30天 = 43,200分钟）中停机43分钟，则其可用性为 (43,200 - 43) / 43,200 ≈ 99.9%。每增加一个“九”，允许的停机时间就减少一个数量级，而实现它的难度和成本也呈指数级增长。

| 可用性等级 | 百分比 | 每月允许停机时间 | 每年允许停机时间 | 典型需求 |
|-----------|--------|------------|------------|---------|
| 2个九 | 99% | 7.3 小时 | 3.65 天 | 内部工具 |
| 3个九 | 99.9% | 43 分钟 | 8.76 小时 | 标准业务系统 |
| 4个九 | 99.99% | 4.3 分钟 | 52.6 分钟 | 电商、SaaS |
| 5个九 | 99.999% | 26 秒 | 5.26 分钟 | 金融、支付 |

::: tip 什么是SLA？
**SLA（服务水平协议）**是服务提供商与客户之间的正式承诺。例如，AWS S3 承诺 99.99% 的可用性；若未达标，将按比例退款。SLA不仅是技术指标——还是商业合同。违反SLA意味着损失资金。
:::

::: tip 3个九与4个九的差距
3个九（99.9%）意味着每月可停机43分钟——一次错误的部署和回滚就可能用完这段时间。4个九（99.99%）意味着每月仅允许4分钟的停机——这需要完整的高可用基础设施，包括自动故障切换、滚动部署和健康检查。
:::

## 2. 故障切换架构

故障切换是高可用性的核心机制：当主节点发生故障时，流量自动切换到备用节点以继续提供服务。

### 主动-备用模式

最常见的高可用架构。主节点处理所有请求，而备用节点实时同步数据但不处理请求。当主节点发生故障时，备用节点会自动接管。

```
Normal state:
  Client → Primary node (handling requests)
            Standby node (syncing data, on standby)

Failover:
  Client → Standby node (takes over as new primary)
            Original primary (failed, awaiting repair)
```

一个关键问题是**分裂大脑**：在网络分区过程中，主节点和备用节点都认为对方宕机，开始发送请求，导致数据不一致。解决方案是引入**Quorum**——至少有3个节点投票决定哪个是主节点。

### 多可用区（Multi-AZ）

在同一区域内，跨多个数据中心（可用性区）部署服务。单个数据中心断电或失去连接不会影响整体服务。云服务提供商通常在可用性区之间提供低延迟专用链路（< 2毫秒）。

### 多区域活跃-活跃

在不同城市甚至不同国家部署完整的服务副本，让每个站点能够独立处理请求。这是高可用性架构的最高级别，但也是最复杂的——核心挑战是**跨区域数据同步**的延迟和一致性问题。

<故障转移策略演示 />

|架构 |可用性等级 |成本 |复杂度 |用例 |
|------|-----------|------|--------|---------|
|单台 |99%~99.9% |低 |低 |开发/测试，内部工具 |
|主动备用 |99.9%~99.99% |中型 |中型 |中小型企业系统 |
|多通用区 |99.99% |高 |高 |电子商务，SaaS平台 |
|多区域活跃 |99.999% |非常高 |非常高 |金融，大规模互联网 |

## 3.灾难恢复设计：RPO与RTO

灾难恢复设计围绕两个核心指标展开：

|度规 |全名 |含义 |示例 |
|------|------|------|------|
|RPO |恢复点目标 |可容忍的数据丢失程度 |RPO=0 表示不可接受的数据丢失 |
|恢复时间 |恢复时间目标 |可容忍的停机时间 |RTO=5分钟意味着5分钟内恢复 |

### 备选策略与RPO关系

|备份方法 |RPO |成本 |描述 |
|---------|-----|------|------|
|每日全备份 |24小时 |低 |最多一天数据丢失 |
|实时增量备份 |分钟 |中等 |连续binlog/WAL同步 |
|同步复制 |0 |高 |写入必须等待复制验证 |

::: 提示 并非所有数据都需要RPO=0
如果用户头像丢失，可以重新上传（RPO=24小时即可），但支付记录不得丢失任何条目（RPO=0）。根据数据的商业价值来决定备份策略，而非采用一刀切的方法。
:::

## 4.故障检测与恢复

### 4.1 故障检测机制

|机制 |原理 |检测速度 |使用场景 |
|------|------|---------|---------|
|心跳 |定期发送心跳数据包;超时表示失败 |秒 |节点活性检测 |
|健康检查 |HTTP/TCP 探测检查服务状态 |秒数 |负载均衡器后端检测 |
|业务探测 |模拟真实请求以检查业务逻辑 |秒到分钟 |端到端可用性监控 |

**心跳检测的工作原理**：节点A在固定间隔（例如每5秒）向监视器发送“我活着”信号。如果漏接N个连续心跳（例如3个），节点A被视为失败。关键参数是**心跳间隔**和**超时阈值**——间隔太短会增加网络开销，过长则延迟故障检测。

**三层健康检查**：
- **存活探针**：进程是否仍在运行？如果没有，重启它
- **就绪探针**：服务是否能接受请求？如果不能，将其从负载均衡器中移除
- **启动探针**：服务是否完成启动？如果没有，等待——不要误诊为故障

### 4.2 自动恢复机制

| 机制 | 描述 | 常用工具 |
|------|------|---------|
| 自动重启 | 自动重启崩溃的进程 | systemd, PM2, K8s |
| 自动扩展 | 负载增加时自动增加实例 | K8s HPA, 云提供商自动扩展 |
| 熔断/降级 | 下游服务失败时快速失败，防止级联故障 | Hystrix, Sentinel, Resilience4j |
| 限流 | 拒绝超过容量的请求 | Nginx limit_req, API 网关限流 |

**熔断模式说明**：

熔断器的灵感来自电气保险丝——当电流过高时，保险丝会自动跳闸，以保护整个电路免于烧毁。在微服务中，当下游服务失败时，熔断器“跳闸”，使请求快速失败，而不是等待超时。

```
Circuit breaker three states:

  Closed (normal) ──→ failure rate exceeds threshold ──→ Open (tripped)
       ↑                                    │
       │                              wait for cooldown
       │                                    ↓
       └── probe request succeeds ←── Half-Open (testing)
```

- **闭合状态**：正常请求转发，同时跟踪失败率
- **开放状态**：所有请求立即返回错误（快速失败），下游不再调用
- **半开放状态**：冷却期结束后，允许少量探测请求通过。若成功，返回关闭;若失败，保持开放状态

**缓冲**是断路器的配套策略：当断路器触发时，它不会返回错误，而是返回“备份”结果。例如，如果推荐服务宕机，返回热门产品列表;如果用户头像加载失败，显示默认头像。

## 5.混沌工程：主动发现问题

混沌工程的核心理念是：**与其等待失败发生，不如主动制造失败**以验证系统在受控环境中的韧性。

|工具 |创造者 |核心能力 |
|------|--------|---------|
|混沌猴子 |Netflix |随机终止制作实例 |
|混沌网格 |PingCAP |K8s 环境中的故障注入 |
|Litmus |CNCF |云原生混沌工程框架 |
|混沌之刃 |阿里巴巴 |多场景故障注入工具 |

::: 提示 混沌工程实施步骤
1. **定义稳态**：澄清正常系统运行的指标（例如，P99延迟<200毫秒）
2. **形成假设**：如果节点宕机，系统应在30秒内自动恢复
3. **注入失败**：创建受控失败（从测试开始，然后进入生产环境）
4. **观察结果**：系统是否如预期恢复？是否存在连锁故障？
5. **修正弱点**：基于发现改进架构和流程
:::

## 摘要

高可用性不是特性，而是一种架构能力。它需要在设计、开发、部署和运营的每个阶段都采取保障措施。

本章的主要收获：

1. **九级**：每增加九颗，停机时间减少一个数量级，成本和复杂度呈指数增长
2. **故障切换**：从主动备用到多区域主动主动，根据业务需求选择合适的架构
3. **RPO和RTO**：基于数据价值和业务容忍度设计备份和恢复策略
4. **自动化**：故障检测、自动重启、断路器和降级是基本的高可用性基础设施
5. **混沌工程**：主动注入故障以验证系统在受控环境中的韧性
