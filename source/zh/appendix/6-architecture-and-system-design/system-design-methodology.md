## 1.四步系统设计方法

系统设计不是一开始就画架构图。无论是面试还是实际操作，你都应该遵循有结构的流程。

<SystemDesignSteps演示 />

::: 提示 为什么先澄清要求？
很多人一拿到提示就开始画图，结果设计出“正确但不是面试官想要的”系统。花5分钟澄清要求可以避免30分钟的重做。

常见的澄清问题：
- 系统的核心功能是什么？（不要设计所有功能）
- 用户规模是多少？（决定是否需要分发）
- 读写比率是多少？（确定缓存策略）
- 数据需要保存多久？（确定存储方案）
:::

## 2.容量估算：包内计算的艺术

“包内估算”是系统设计中的核心技能。你不需要精确计算——只需知道数量级就足够了。

<容量估计演示 />

### 常见转换快速参考

|大小 |转换 |记忆技巧 |
|------|------|---------|
|1天 |86,400秒 |≈ 100K秒 |
|每天1亿请求 |≈ 1200 QPS |除以10万 |
|1 KB × 100M |≈ 100 GB |100M 小记录 |
|1MB 1M × 1M |≈ 1TB |1M 图像 |

### 估算中的80/20法则

大多数系统遵循80/20规则：20%的数据处理80%的请求。这意味着：

- **缓存大小** ≈ 总数据量× 20%
- **快捷键QPS** ≈总QPS×80%集中在20%的键上
- **缓存命中率**目标80%≈（以下提示缓存策略存在问题）

## 3.核心设计模式

系统设计中反复出现的模式——掌握这些模式能让你为大多数情况做好准备。

### 3.1 缓存模式

|模式 |读取路径 |写路径 |用例 |
|------|--------|--------|---------|
|缓存侧 |先检查缓存;未命中时查询数据库并回填 |先写数据库，然后使缓存失效 |通用，最常用 |
|读通 |缓存层自动从数据库加载 |与缓存侧面相同 |需要缓存框架支持 |
|写后 |与缓存侧相同 |先写缓存，异步写入数据库 |重写，能容忍数据丢失 |

::: 提示 为什么用“使缓存失效”而不是“更新缓存”？
在并发情况下，更新缓存容易出现数据不一致：线程A和线程B同时更新，A先写入数据库，但B先更新缓存，导致缓存中B值过时。使缓存失效会导致下一次读取请求从数据库重新加载，自然避免了此问题。
:::

### 3.2 数据库分片

当单个表超过数千万行，或者单一数据库的QPS出现瓶颈时，就该考虑数据库分片了。

|策略 |方法 |优点 |缺点 |
|------|------|------|------|
|垂直分片 |按业务域分割数据库 |业务解耦，独立扩展 |跨数据库JOIN较难 |
|水平分片 |按规则将一张表拆分为多个表 |每张表的数据量可控 |分片键的选择至关重要 |
|垂直表格拆分 |将大列拆分为独立表 |减少I/O，提高查询效率 |需要额外的JOIN次数 |

**分片密钥选择原则**：
- 选择查询频率最高的字段（例如，user_id）
- 数据分布应均匀以避免热点
- 尽量将同一用户的数据保持在同一分片上（以减少跨分片查询）

### 3.3 消息队列

消息队列是分布式系统的“缓冲器”。它们的核心作用是解耦、异步处理和峰值削减。

|场景 |无队列 |有队列 |
|------|---------|--------|
|订单后发送通知 |订单 API 同步调用通知服务;通知失败导致订单失败 |订单成功后发送消息;通知服务异步消耗 |
|闪购 |突发流量使数据库不堪重负 |请求先进入队列;后端进程按自己的节奏进行 |
|数据同步 |服务A直接调用服务B的API！服务A发布事件;服务B订阅并处理事件 |

## 4.权衡思维：没有万能灵丹

架构设计的本质在于权衡。每个决策都有成本——关键在于理解成本并做出适合当前阶段的选择。

|权衡维度 |选项A |选项B |决策基础 |
|---------|--------|--------|---------|
|一致性与可用性 |强一致性（CP） |高可用性（AP） |企业能否容忍短暂的不一致？|
|性能与成本 |全缓存 |按需缓存 |数据量与预算 |
|简洁与灵活性 |单体架构 |微服务 |团队规模与业务复杂性 |
|实时与批处理 |流处理 |批处理 |数据时效性要求 |
|自托管与托管 |自己构建MySQL |使用云数据库 RDS |运营能力与成本 |

::: 提示 架构决策记录 (ADR)
每一个重要的架构决策都应该被记录：**当时的背景、考虑了哪些选项、为什么选择了这个方案，以及有哪些权衡**。这不是为了指责谁——而是为了帮助未来的团队理解“为什么会这样设计”。

格式很简单：
- **标题**：使用 X 而不是 Y
- **背景**：我们遇到的问题
- **决策**：我们选择的解决方案
- **理由**：我们选择此方案的原因
- **后果**：此决策的缺点和风险
:::

### 常见的权衡错误

| 错误 | 表现 | 正确做法 |
|------|------|---------|
| 过早优化 | 在 1,000 日活跃用户时进行分片 | 从单个数据库开始；当遇到瓶颈时再分片 |
| 技术驱动 | “我想使用 Kafka” 而不是“我需要异步处理” | 从问题出发，而不是从技术出发 |
| 忽视运维成本 | 选择团队无法维护的最优方案 | 解决方案必须匹配团队能力 |
| 追求完美一致性 | 在每种场景下使用分布式事务 | 对大多数场景来说，最终一致性就足够 |

## 5. 经典案例研究

让我们通过三个经典示例来联系所学的方法。

### 5.1 URL 缩短器 (TinyURL)

URL 缩短器是经典的系统设计面试题——小而全面。

**需求澄清**：
- 核心功能：长 URL → 短 URL（写入），短 URL → 重定向（读取）
- 读写比例：约 100:1（读取远远多于写入）
- 每日重定向次数：1亿
- 短 URL 永不过期

**容量估算**：

| 指标 | 计算 | 结果 |
|------|------|------|
| 写入 QPS | 100M / 100 / 86,400 | ≈ 12 QPS |
| 读取 QPS | 100M / 86,400 | ≈ 1,200 QPS |
| 峰值读取 QPS | 1,200 × 3 | ≈ 3,600 QPS |
| 5 年存储 | 1M/天 × 365 × 5 × 100B | ≈ 18 GB |
| 缓存 (20%) | 18 GB × 20% | ≈ 3.6 GB |

**架构设计**:

```
Write path: Client → API Server → ID Generator → Base62 Encode → Write to MySQL + Redis
Read path: Client → CDN → API Server → Redis lookup → 302 redirect
                                    ↓ (cache miss)
                                  MySQL query → backfill Redis
```

**关键设计决策**：
- 短链接生成：Snowflake 分布式 ID、Base62 编码以避免哈希冲突
- 缓存策略：Cache-Aside，热点短链接使用 CDN 加速
- 数据库：单表足够（18GB 很小），按短码建立索引

### 5.2 信息流系统

社交平台信息流（微信朋友圈、Twitter 首页时间线）是另一经典问题。

**核心挑战**：用户发布一条动态后，如何让所有粉丝都看到？

| 方法 | 工作原理 | 优势 | 劣势 |
|------|------|------|------|
| Pull 模型 | 在读取时实时聚合关注者的动态 | 写入简单，存储少 | 读取慢；关注者多时延迟高 |
| Push 模型 | 在发布时写入所有粉丝的收件箱 | 读取极快 | 粉丝多的账号写放大严重 |
| 混合（Push-Pull） | 普通用户使用推，名人使用拉 | 读写性能均衡 | 实现复杂 |

**混合 Push-Pull 方法**：
- 粉丝 < 1 万：在发布时推送到所有粉丝的 feed 缓存（Push 模型）
- 粉丝 > 1 万：不推；粉丝读取时实时拉取（Pull 模型）
- 用户打开信息流时：合并推送内容与实时拉取的名人内容，按时间排序

### 5.3 秒杀系统

秒杀的核心挑战：瞬时超高并发，库存不能超卖。

**流量特征**：
- 秒杀开始前：大量用户刷新页面等待
- 秒杀瞬间：QPS 可达平时的 100 倍或更多
- 秒杀结束后：流量快速下降

**分层削峰策略**：

```
User request → CDN (static pages) → Gateway (rate limiting) → Message queue (peak shaving) → Inventory service (deduction)
```

| 层 | 策略 | 效果 |
|------|------|------|
| 前端 | 按钮灰化   随机延迟   CAPTCHA | 过滤机器人，分散请求 |
| CDN | 静态资源缓存 | 减少90%的页面请求 |
| 网关 | 令牌桶限流 | 只允许系统可处理的流量 |
| 消息队列 | 请求排队，异步处理 | 峰值削峰，保护数据库 |
| 库存服务 | Redis 预扣减   Lua 原子操作 | 防止超卖，毫秒级响应 |

::: tip 秒杀核心原则
1. **尽可能在上游拦截**：如果可以在 CDN 阻止，就不要让请求到达应用层
2. **读写分离**：商品详情页使用缓存；只有订单操作才访问数据库
3. **异步处理**：用户点击“购买”后，立即返回“排队中”，后台处理
4. **备用方案**：限流、熔断、降级——每一层都需要 Plan B
:::

## 总结

系统设计是一项高度实用的技能。核心在于结构化思维和权衡取舍。

本章要点：

1. **四步框架**：需求澄清 → 容量估算 → 架构设计 → 深度优化——每一步都很关键
2. **粗略估算**：不需要精确，只要知道数量级即可指导架构决策
3. **核心模式**：缓存、数据库分片、消息队列、CDN、限流、熔断——这些是系统设计的“积木块”
4. **权衡思维**：没有完美方案，只有适合当前阶段的方案——记录每次决策的理由和成本
5. **经典案例**：URL 短链接用于基础练习，Feed 系统用于推拉模型，秒杀用于高并发——掌握这三类可以类比推演
