# 从单体到微服务演进简介

::: tip 简介
**没有哪种架构是“最优”的——只有“最适合当前阶段”的架构。** 从单体架构迁移到微服务架构不是一次性的飞跃，而是随着业务规模和团队规模增长的逐步演进。过早拆分成微服务和过晚拆分一样危险。
:::

- **演进路径**：了解从单体到微服务的四个阶段

- **拆分策略**：掌握按业务领域进行拆分的方法论
- **通信模式**：了解同步与异步服务间通信的选择

## 1. 架构演进路径

架构演进不是由技术驱动的——它是**由组织规模驱动的**。当团队规模从5人增长到500人时，单体架构的协作效率会急剧下降。

| 阶段 | 架构 | 团队规模 | 特征 |
|------|------|---------|------|
| 初创期 | 单体应用 | 1–10人 | 所有代码在一个项目中，部署简单 |
| 成长期 | 模块化单体 | 10–50人 | 按模块组织代码，但仍然一起部署 |
| 扩展期 | SOA（面向服务架构） | 50–200人 | 按业务线拆分为粗粒度服务 |
| 扩张期 | 微服务 | 200人 | 细粒度服务，每个团队独立开发和部署 |

::: tip 康威定律
“设计系统的组织……会产生反映其沟通结构的设计。” — Melvin Conway

简单说：3个团队构建一个系统，最终会形成3个服务。架构拆分的本质是**组织拆分**。

**逆康威定律**：由于组织结构决定系统架构，为了获得所需架构，必须首先调整组织结构。例如，如果你想要一个独立的支付服务，首先要建立一个独立的支付团队。许多公司在微服务拆分失败并不是因为技术问题，而是因为组织没有适应。
:::

## 2. 拆分微服务的标准

并非所有系统都需要微服务。过早拆分会引入不必要的复杂性。

| 信号 | 描述 | 建议 |
|------|------|------|
| 频繁的部署冲突 | 多个团队修改同一代码库，冲突频繁 | 考虑拆分 |
| 模块需要独立扩展 | 搜索模块所需资源是其他模块的10倍 | 考虑拆分 |
| 需要差异化技术栈 | AI模块使用Python，主站使用Java | 考虑拆分 |
| 团队人数<10人 | 通信开销低，单体足够 | 不要拆分 |
| 业务仍在探索阶段 | 需求变化快，边界不清晰 | 不要拆分 |
| 无DevOps能力 | 无持续集成 / 持续部署、容器化或监控基础设施 | 不要拆分 |

## 3. 拆分策略

### 3.1 按业务领域拆分（DDD界限上下文）

DDD（领域驱动设计）中的界限上下文是拆分微服务的最佳指导原则。每个界限上下文对应一个独立的业务领域，拥有自己的数据模型和业务规则。

**什么是界限上下文？** 同一个词在不同业务领域可能有不同含义。例如，“用户”在用户领域指注册信息（姓名、邮箱），在订单领域指购买者（收货地址、支付方式），在推荐领域指行为画像（浏览历史、偏好标签）。界限上下文划定了一个边界，在这个边界内术语和模型有明确统一的含义。

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  User Domain │  │ Order Domain│  │Payment Domain│
│             │  │             │  │             │
│ User        │  │ Order       │  │ Payment     │
│ Profile     │  │ OrderItem   │  │ Refund      │
│ Address     │  │ Cart        │  │ Transaction │
│             │  │             │  │             │
│ User Service│  │Order Service│  │Payment Svc  │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │                │                │
       └────── API calls / event communication ───────┘
```

| 有界上下文 | 核心实体 | 对应服务 |
|-----------|---------|---------|
| 用户领域 | 用户, 个人资料, 地址 | 用户服务 |
| 产品领域 | 产品, 分类, SKU | 产品服务 |
| 订单领域 | 订单, 订单项 | 订单服务 |
| 支付领域 | 支付, 退款 | 支付服务 |
| 物流领域 | 发货, 追踪 | 物流服务 |

### 3.2 蔓生图模式

不要一次性重写整个单体应用。相反，就像蔓生图一样，逐步用新服务替换旧模块：

1. 在单体应用之外创建新服务
2. 通过代理层将部分流量路由到新服务
3. 在确认新服务稳定后，逐步迁移更多流量
4. 最终完全替换旧模块

## 4. 服务通信模式

| 方法 | 协议 | 特点 | 使用场景 |
|------|------|------|---------|
| REST | HTTP/JSON | 简单且通用，生态完善 | 外部API，CRUD操作 |
| gRPC | HTTP/2  Protobuf | 高性能，强类型 | 高频内部服务调用 |
| 消息队列 | AMQP/Kafka | 异步解耦，削峰填谷 | 事件通知，异步任务 |
| GraphQL | HTTP/JSON | 客户端驱动查询 | BFF层，移动端客户端 |

::: tip 同步 vs 异步选择
- **需要立即结果** → 同步 (REST/gRPC)
- **不需要立即结果** → 异步 (消息队列)
- **一个事件触发多个动作** → 异步 (发布-订阅)

经验法则：尽量使用异步。同步调用链越长，系统越脆弱。
:::

## 5. 数据拆分：最难的部分

微服务拆分中最痛苦的部分不是代码拆分，而是数据库拆分。每个服务应拥有自己的数据库，但这会使跨服务查询变得困难。

| 挑战 | 描述 | 解决方案 |
|------|------|---------|
| 跨服务 JOIN | 无法直接 JOIN 两个服务的表 | API组合查询，数据冗余 |
| 分布式事务 | 跨数据库事务无法使用本地事务 | Saga，本地消息表 |
| 数据一致性 | 服务间数据可能暂时不一致 | 最终一致性，事件驱动 |
| 数据迁移 | 从共享数据库迁移到独立数据库 | 双写过渡，数据同步工具 |

## 总结

从单体到微服务是一个渐进过程，而非一夜革命。

本章关键要点：

1. **演进路径**：单体 → 模块化单体 → SOA → 微服务，每一步都源于明确动机
2. **何时拆分**：团队规模、部署冲突、扩展需求是拆分信号
3. **拆分策略**：使用DDD有界上下文指导拆分，利用蔓生图模式进行渐进迁移
4. **通信选择**：尽量异步；同步调用链保持最短
5. **数据拆分**：最难但最重要——接受最终一致性是关键思维转变
