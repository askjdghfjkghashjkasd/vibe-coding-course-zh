## 1. URL 解析

::: tip 核心问题
**为什么 URL 会长这样？** `https://www.example.com:8080/path/page.html?id=123#section` — 这串字符实际上是什么意思？
:::

### 类比：填写订购单

如果你在订单上只写了“买鞋”，仓库不会知道该发送哪一双。你需要说明：

- **商店类型**（官方旗舰店 / 普通商店）
- **商店名称**（耐克官方店）
- **产品位置**（男士鞋 / 跑步系列）
- **具体型号**（Air Max 90）
- **特别说明**（我想要红色的）

### 实际流程：URL 解析流程

**URL（统一资源定位符）**是浏览器世界的“产品定位码”。当你在地址栏输入 `https://www.example.com:8080/path/page.html?id=123#section` 时，浏览器会立即将其拆解：

| URL 部分 | 示例值 | 购物类比 | 技术用途 |
| -------------------------- | -------------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| **协议** `https://` | 安全超文本传输协议 | **运输方式**：安全配送（HTTPS）vs普通配送（HTTP） | 决定通信规则。`http` 是普通传输，`https` 是加密传输 |
| **域名** `www.example.com` | 服务器的可读名称 | **商店名称**：京东超市 | 告诉浏览器要去哪个服务器。域名方便人记忆，最终必须转换为 IP 地址 |
| **端口** `:8080` | 服务器的特定“门号” | **柜台号**：柜台 #3（默认省略） | 服务器可能有多个服务，端口指定访问哪一个。HTTP 默认 80，HTTPS 默认 443 |
| **路径** `/path/page.html` | 服务器上的文件位置 | **货架位置**：日用品区 / 第三排 | 指定服务器上资源的具体位置 |
| **查询参数** `?id=123` | 额外信息 | **订单备注**：红色，XL 尺码 | 传递给服务器的额外数据，如搜索关键词和页码 |
| **片段** `#section` | 页面内的位置 | **手册页码参考**：翻到第 5 页 | 页面加载完成后自动滚动到指定位置；不会发送到服务器 |

<UrlParserDemo />

::: info 关键理解
URL 的存在是为了让**人类**能够记住和输入它们。计算机最终需要的是**IP 地址**（就像快递员需要实际仓库地址，而不仅仅是“耐克官方店”这个名字）。
:::

## 2. DNS 查询

::: tip 核心问题
**浏览器如何找到网站？** 你输入一个可读域名（如 `baidu.com`），但计算机真正需要的是数字地址（IP）。中间发生了什么？
:::

### 类比：查找仓库地址

你在订单上写了“耐克官方店”，但物流系统不知道仓库在哪。它需要查阅地址簿：

1. 首先检查**最近的地址**（我最近有没有在这家店买过东西？）→ 浏览器缓存
2. 如果没有，问问**邻近投递点**（他们知道大致的区域分配）→ 本地域名服务器
3. 问问**总部调度中心**（知道谁管理 .com 商店）→ 根域名服务器
4. 问问**品牌管理办公室**（最终找到 Nike 商店的真实配送仓库）→ 权威域名服务器

### 实际流程：DNS 分层查询流程

**DNS（域名系统）**是互联网的“分布式地址簿查询系统”。由于全球有数十亿个域名，因此使用分层架构来分散查询负载：

```
You (Browser)
    ↓ Ask: What's the IP for google.com?
Local DNS server (your ISP, such as China Telecom/China Unicom)
    ↓ Ask: Who manages .com?
Root name server (13 root server groups worldwide, managing all top-level domains)
    ↓ Tell: Ask the .com manager
Top-level domain server (Verisign manages .com)
    ↓ Tell: Ask the google.com manager
Authoritative name server (Google's own DNS server)
    ↓ Tell: google.com's IP is 142.250.80.46
Return IP address to browser
```

**查询类型说明：**

- **递归查询**：浏览器只发送一次请求，本地 DNS 负责查询所有层级并返回结果
- **迭代查询**：每一层只告诉下一层去哪里查找；浏览器需要多次查询
- **缓存机制**：查询结果被缓存，下次可直接返回，大大加快访问速度

<DnsLookupDemo />

::: info 为什么有这么多层？
想象一下，如果全世界只有一本通讯录——数十亿人同时查询它，它会立刻崩溃。分层设计让每一层只管理自己的“管辖范围”，使其高效且可靠。

这是互联网的核心设计原则：**分布式系统**。
:::

## 3. TCP 连接建立：三次握手

::: tip 核心问题
**为什么需要“三次握手”？** 找到服务器地址后，为什么不能直接发送数据？为什么要先进行三轮通信？
:::

### 类比：建立物流通道

如果物流卡车直接开往仓库，可能结果是：

- 仓库闭门 → 白跑一趟
- 仓库超载且不接单 → 无法发货
- 找不到装货码头 → 无法连接

**所以在实际运输货物前，必须先建立可靠的运输通道。**

### 实际过程：TCP 三次握手流程

**TCP（传输控制协议）**是保证数据可靠传输的协议。在传输货物（数据）之前，必须通过“三次握手”建立连接：

```
Client (Your Computer)              Server (Merchant Warehouse)
   |                                |
   |--- SYN=1 --------------------->|  1st: Hello, I'm home and ready to receive! (SYN)
   |                                |
   |<-- SYN=1, ACK=1 ---------------|  2nd: Got it! I'm ready to ship too. Are you home? (SYN-ACK)
   |                                |
   |--- ACK=1 --------------------->|  3rd: Yes! Please ship. (ACK)
   |                                |
   ===== Channel established, shipping begins =====
```

**为什么要三次，而不是两次？**

- **第一次（SYN）**：客户端证明它能发送数据
- **第二次（SYN-ACK）**：服务器证明它能接收并发送数据
- **第三次（ACK）**：客户端证明它能接收数据

三次握手确保：**双方都能发送并都能接收**——满足可靠传输的所有四个条件。

**TCP 还负责：**

- **数据分段**：将大数据分成较小的数据包进行传输
- **顺序重组**：确保数据包按正确顺序组装
- **错误重传**：自动重新发送丢失的数据包
- **流量控制**：根据网络情况调整发送速度

<TcpHandshakeDemo />

> **HTTPS 额外步骤**：对于 HTTPS（安全网站），在 TCP 握手之后，还会进行 **TLS 握手**（1-RTT 或 2-RTT）。双方交换加密密钥，确保只有双方能理解后续通信——就像用秘密代码交流。

## 4. HTTP 协议：请求与响应

::: tip 核心问题
**浏览器和服务器之间在说什么？** 建立连接后，浏览器如何“告诉”服务器它想要什么？服务器又如何“回应”？
:::

### 类比：下单、发货和订单确认

物流车辆到达仓库：“这是订单（HTTP 请求），**我想取到商品（网页 HTML 源码）！**”
仓库管理员核实：“订单有效。这是你的包裹（**HTML 文件**），请取走。”

### 实际流程：HTTP 通信流程

**HTTP（超文本传输协议）**是浏览器与服务器之间的“对话规则”。在通道建立后，浏览器发送一个**取货请求**。**核心目标是获取网页的源代码（HTML 文件）**：

**HTTP 请求示例：**

```http
GET /index.html HTTP/1.1          ← Request method + path + protocol version
Host: www.example.com             ← Target host (supports virtual hosting; one server can host multiple websites)
User-Agent: Chrome/120.0          ← Client identifier (server can return adapted content based on this)
Accept: text/html,application/xhtml+xml  ← Acceptable response formats
Accept-Language: zh-CN,zh;q=0.9   ← Preferred languages
Accept-Encoding: gzip, deflate    ← Supported compression formats
Connection: keep-alive            ← Keep connection alive (reuse TCP connection)
Cookie: session_id=abc123         ← Authentication credentials
```

::: tip 开发者顿悟：这不就是一个 API 吗？
**完全一样！**
你编写的 API 调用 (`fetch` / `axios`) 与浏览器访问网页，在 HTTP 层面上**完全一样**。

两者都会发送请求，服务器返回文本数据。

- 如果服务器返回 **HTML**，浏览器会**渲染**它（将其转换为网页）。
- 如果服务器返回 **JSON**，你的代码会**存储**它（用于逻辑处理）。

**并不存在“两种类型”的请求——只有一种 HTTP 请求。区别只是响应数据的格式（Content-Type）。**
这就是为什么理解 HTTP 就等于理解 90% 的后端 API 原理。

如果你想更深入了解 API 开发，请参考 [API 章节](./api-intro.md)。
:::

**常用 HTTP 方法：**

- `GET`：获取资源（安全、幂等、可缓存）
- `POST`：提交数据（创建资源，例如注册、登录）
- `PUT`：更新资源（完整替换）
- `PATCH`：部分更新资源
- `DELETE`：删除资源
- `HEAD`：仅获取响应头（不返回主体；用于检查资源是否存在）

**服务器返回 HTTP 响应：**

```http
HTTP/1.1 200 OK                   ← Protocol version + status code + status description
Date: Mon, 23 May 2025 12:00:00 GMT  ← Server time
Content-Type: text/html; charset=UTF-8  ← Content type and encoding
Content-Length: 1234              ← Content length (bytes)
Cache-Control: max-age=3600       ← Caching policy
Set-Cookie: user_id=xyz789        ← Set Cookie

<!DOCTYPE html>...                ← Response body (webpage content)
```

**HTTP 状态码类别：**

|状态代码 |类别 |含义 |现实生活类比 |
|----------- |---------- |---------------- |-------------------------------- |
|**200** |成功 |请求已成功处理 |“订单确认，发货中” |
|**301/302** |重定向 |资源已迁移 |“本店已迁移，请在新地点下单” |
|**304** |未修改 |缓存仍然有效 |“你上次买的东西还能用，无需重新发货” |
|**400** |客户端错误 |请求格式错误 |“订单不清晰且无法读取” |
|**401** |未授权 |需要身份验证 |“请先出示会员卡” |
|**403** |禁止 |权限不足 |“仅限工作人员，禁止进入” |
|**404** |未找到 |资源不存在 |“本产品无库存” |
|**500** |服务器错误 |内部服务器错误 |“仓库着火了，暂时无法发货” |
|**502** |网关故障 |上游服务器无响应 |“主仓库缺货，分支也无法传输” |
|**503** |服务不可用 |服务器过载或维护中 |“订单过多，暂时暂停” |

## 5.浏览器渲染引擎

::: 提示 核心问题
**代码如何变成视觉展示？** 服务器发送枯燥的HTML/CSS/JavaScript代码。浏览器如何将其变成丰富多彩的网页？
:::

### 类比：开箱与组装

你终于收到了送货包裹（HTTP 响应），但打开时，它并不是现成家具——而是一堆**零件**（HTML）和一本**组装手册**（CSS）。作为“买家”（浏览器），你需要自己组装：

1. **打开包装**：取出所有部件并检查列表（解析HTML→DOM树）。
2. **阅读手册**：理解说明——哪个部分放哪里，什么颜色（解析CSS→CSSOM树）。
3. **分类和整理**：挑选组装零件，丢弃泡沫（`display: none`），准备组装（构建渲染树）。
4. **测量位置**：用尺子测量房间尺寸，确定每件家具的布局/重新焊接位置。
5. **涂漆和装饰**：在家具上涂漆和贴纸（涂漆）。
6. **最终显示**：清理并开灯进行显示（合成）。

### 实际流程：页面渲染流程

浏览器接收到的是**HTML/CSS/JavaScript代码**（干文本），但它需要变成**像素图像**（一个漂亮的网页）。这个过程称为**渲染**，由浏览器的**渲染引擎**执行（如Chrome的Blink、Safari的WebKit）。

#### 步骤1：解析HTML→构建DOM树（零件列表）

浏览器读取HTML字节流并将其解析为**DOM（文档对象模型）树**。这就像将一堆分散的部分组织成一个层级结构的列表：

```html
<!-- Original HTML -->
<div class="header">Title</div>
<div class="content">Content</div>
```

```text
DOM tree structure:
Document
 └─ html
     └─ body
         ├─ div.header ("Title")
         └─ div.content ("Content")
```

#### 步骤 2：解析 CSS → 构建 CSSOM 树（手动）

浏览器解析所有 CSS（内联、外部文件）并构建 **CSSOM（CSS 对象模型）树**。这就像在手册中理解样式规则一样：

```css
.header {
  color: blue;
  font-size: 24px;
} /* Title should be blue */
.content {
  display: none;
} /* Content temporarily hidden */
```

#### 步骤3：合并渲染树→（准备组装）

DOM 树 CSSOM 树 = **渲染树**。
关键点：**渲染树中只有“可见”元素。**

- `.header`：在渲染树中（可见）。
- `.content`：**在渲染树中不**（因为`display: none`，就像不需要组装的废弃包装纸）。

####步骤4：布局（回流）— 测量尺寸

浏览器会在屏幕上计算渲染树中每个节点的**精确坐标和大小**。

- “此标题框宽100像素，高50像素，位于屏幕坐标（0,0）。”
- 此过程称为**reflow**。如果窗口大小发生变化（例如旋转电话），所有元素位置都必须重新计算——这对性能非常耗费。

#### 步骤5：上色 — 上色

知道位置后，浏览器开始填充像素：绘制背景色、文本颜色、边框、阴影等。

#### 第6步：合成——最终展示

现代浏览器将页面划分为多个**图层**用于独立绘画（例如3D变换、独立滚动条图层），GPU像Photoshop图层一样将它们合成到屏幕上。

<BrowserRenderingDemo />

::: 信息 你知道吗？
**布局和绘画**是浏览器最忙碌的时候。页面结构元素越多、越复杂，浏览器计算位置和绘制颜色所需的时间就越多。这就是为什么有些复杂页面会显得迟缓。
:::

## 5.5 页面生成方法：静态网站与动态网站

::: 提示 核心问题
**网页内容从哪里来？** 我们讲过浏览器如何渲染页面，但服务器上的HTML文件是如何到达那里的？它是提前准备还是按需制作？
:::

到目前为止，我们讨论的都是浏览器如何“打开包”——将服务器发送的 HTML/CSS/JS 渲染成页面。但你有没有想过：**服务器上的那个 HTML 文件最初是怎么出现的？**

答案是：**有两种方式**——这就是静态网站和动态网站的区别。

### 静态网站：预设并直接提供

想象一下去超市买饼干。货架上的饼干已经在工厂生产——你只需取货，无需等待。

**静态网站**的工作原理相同——网页已经在服务器上准备好了。当你访问时，服务器会直接发送现成的HTML文件，无需额外处理。

**特征：**
- 快速访问（服务器只需发送文件，无需计算）
- 创建简单（只需写 HTML，即可完成）
- 高容量（可使用 CDN 分发;处理任何流量）
- 内容难以更新（更改内容需要重新生成文件）

**常见示例：** 公司简介页面、产品文档、帮助中心、个人博客

### 动态网站：按订单制作，每次都不同

现在想象一下，去餐厅点餐。厨师会根据你的点单现做菜——如果你点了宫保鸡丁，就不会有糖醋肉。

**动态网站**会在你访问时“现场”生成页面——服务器在收到请求后查询数据库、计算数据，并为你生成全新的HTML文件。

**特点：**
- 实时内容（购物车显示最新库存，新闻即时更新）
- 个性化（登录后可看到自己的个人资料）
- 功能强大（搜索、评论、推荐、支付等功能全部可用）
- 访问较慢（服务器需要时间计算）
- 服务器负载高（大量同时访问可能需要排队）

**常见示例：** 淘宝、微博、网银、在线文档

**需要服务器吗？** 动态网站确实需要某种“后端”来生成内容，但形式各异：
- **传统服务器**：购买/租用自己的服务器（阿里云 ECS、AWS EC2）
- **无服务器架构**：无需管理服务器；由云服务提供商运行你的代码（AWS Lambda、阿里云函数计算、Cloudflare Workers）
- **第三方 API 调用**：使用 Stripe 处理支付，使用天气局 API 获取天气 — 无需自己编写后端代码

::: tip 结合静态和动态
如今许多网站是“混合型”的：主页结构为静态，但某些部分（如评论区、搜索框）是动态加载的。JavaScript 可以在页面加载后调用 API 获取数据，实现“静态页面 + 动态功能”。
:::

### 静态网站与动态网站的清晰对比

| | 静态网站 | 动态网站 |
|---|---------|---------|
| **生成方式** | 预先制作，存储在服务器上 | 访问时按需生成 |
| **类比** | 超市货架上的商品 | 餐厅现点现做的菜 |
| **速度** | 快 | 较慢（需要计算） |
| **内容可以更改吗？** | 困难（需要重新生成） | 容易（后端更改即可） |
| **适合用途** | 展示内容（个人资料、文档） | 交互应用（购物、社交） |
| **典型示例** | 公司官网、帮助文档 | 淘宝、微信、网银 |

### 常见问题

**问：静态网站不能使用 JavaScript 吗？**

当然可以！轮播图、下拉菜单、表单验证等交互功能都可以在静态网站上通过 JavaScript 实现。当我们说“静态”和“动态”时，指的是**页面内容是否预先准备好**，而不是是否有交互功能。

**问：动态网站必须购买自己的服务器吗？**

不一定。除了传统服务器，你可以使用无服务器架构（云函数）或直接调用第三方 API。目前趋势是“尽量避免直接管理服务器” — 使用静态网站 + JavaScript API 调用以提高速度和降低成本。

::: tip 重要提醒
无论网站是静态还是动态，**浏览器渲染原理完全相同！** 浏览器会渲染服务器发送的内容。唯一的区别是：
- 静态网站：服务器发送“成品”
- 动态网站：服务器发送“新鲜制作”的内容

作为前端开发者，你的主要关注点是浏览器如何处理接收到的内容，而不是服务器如何生成内容。
:::

让我们回顾整个流程：

|阶段 |技术术语 |购物类比 |核心任务 |关键技术 |
|----------- |---------- |-------- |------------------ |------------------------------ |
|**1.解析** |URL解析 |填写订单 |了解买家的需求 |协议、域、端口、路径、参数 |
|**2.查找** |DNS查询 |查找仓库地址 |查找商店的运输仓库 |递归/迭代查询，缓存 |
|**3.连接** |TCP握手 |建立信道 |确保物流顺畅 |三方握手、序列号、流量控制 |
|**4.交换** |HTTP交换 |仓库运输 |提交订单和接收货物 |请求方法、状态码、头字段 |
|**5.显示** |浏览器渲染 |开箱与组装 |展示产品 |DOM，CSSOM，渲染树，布局，绘制 |

- 解析复杂地址
- 分布在全球的查询DNS服务器
- 与数千英里外的服务器建立了可靠的连接
- 完成完整的HTTP对话
- 将干代码变成了精美的视觉展示

这就是互联网的魅力：**复杂技术，简单体验。**

## 7.术语表

|术语 |全名 |简单说明 |
|----------- |----------------------------- |-------------------------------------------------------------------------- |
|** URL** |统一资源定位器 |网页的“地址”，告诉浏览器资源的位置。|
|**DNS** |域名系统 |互联网的“电话簿”，将人类可读的域名转换为机器可读的IP地址。|
|**IP地址** |互联网协议地址 |每个联网设备的唯一“门号”，如`192.168.1.1`。|
|**TCP** |传输控制协议 |确保数据传输可靠，通过三方握手建立连接的“规则”。|
|**HTTP** |超文本传输协议 |浏览器与服务器之间“对话”的规则。|
|**HTTPS** |HTTP 安全 |**安全 HTTP**。在 HTTP 之上添加加密（TLS/SSL）以保护数据安全。|
|**HTML** |超文本标记语言 |网页的“骨架”，定义内容结构。|
|**CSS** |层叠样式表 |网页的“皮肤”，定义内容外观。|
|**DOM** |文档对象模型 |浏览器将HTML转换为更便捷操作的树状结构。|
|**CSSOM** |CSS 对象模型 |浏览器将 CSS 转换为的树状结构。|
|**渲染** |浏览器将代码转换为屏幕像素的过程。|
|**RTT** |往返时间 |数据包发送及其确认的时间，影响网页加载速度。|
