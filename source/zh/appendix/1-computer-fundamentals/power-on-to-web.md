# 计算机系统概览：从开机到访问网页

::: tip 前言
你是否曾想过，从按下电脑电源按钮到最终在浏览器中看到网页之间发生了什么？

这个过程就像一场**接力赛**——硬件上电并唤醒固件，固件完成检查后将接力棒交给操作系统，操作系统准备好环境以便浏览器运行，浏览器再通过网络从远程服务器获取网页。每一步都**依赖于前一步的成功完成**。如果任何一名选手掉了接力棒，后续步骤就无法继续。

理解这条完整链条将帮助你建立对计算机系统的整体认识，也是成为全栈工程师的必经步骤。
:::

**你将学到什么？**

本文将按照事件实际发生的顺序，指导你了解从按下电源按钮到看到网页的五个阶段：

1. **硬件启动**（第1节）→ 电流如何唤醒CPU  
2. **固件自检**（第2节）→ BIOS/UEFI 如何确认硬件正常并找到启动设备  
3. **操作系统启动**（第3节）→ 内核如何加载，以及桌面如何显示  
4. **浏览器启动**（第4节）→ 操作系统如何运行一个应用程序  
5. **网络请求**（第5节）→ 从输入URL到页面渲染的完整网络旅程  

每一步都建立在前一步的基础上，不能跳过。

---

## 1. 按下电源：硬件唤醒

### 1.1 电源启动

当你按下电源按钮时，**电源供应单元（PSU）**开始工作，将交流电（220V）转换为直流电（12V、5V、3.3V等），以为所有硬件组件供电。

```
Power button → Power Supply Unit (PSU) → DC output → Powers motherboard components
```

### 1.2 主板芯片唤醒

一旦电源稳定，**主板芯片组**开始工作。它就像计算机的“总调度员”，负责协调所有硬件组件。

### 1.3 CPU 复位

在接收到复位信号后，CPU 会清除所有内部寄存器和缓存，并从预设地址开始执行指令。这个地址通常指向 **BIOS/UEFI** 芯片。

<PowerOnDemo />

---

> **第一棒接力完成** 此时，硬件层级的工作已完成：电源将交流电转换为稳定的直流电，主板芯片组已唤醒并开始协调各组件，CPU 完成复位，清空寄存器，并准备执行其第一条指令。
>
> 但请注意——此刻的 CPU 就像“刚睁眼的新生儿”。它可以执行指令，但对其环境一无所知：安装了多少内存？显卡是否工作正常？硬盘在哪里？应该从哪个设备启动操作系统？CPU 自己无法回答这些问题。
>
> 因此，CPU 复位后执行的第一条指令是跳转到一个**固定内存地址**——该地址指向永久焊接在主板上的 BIOS/UEFI 固件芯片。从这一刻起，控制权从纯硬件转向固件。BIOS/UEFI 的使命明确：**检查所有硬件是否正常运行，然后找到并启动操作系统。**这就是接力的第二棒。

## 2. BIOS/UEFI：硬件自检

<BiosUefiInteractiveDemo />

---

> **第二棒接力完成** BIOS/UEFI 已成功完成三项任务：通过 POST 确认内存、显卡、键盘及其他硬件均正常运行；初始化每个硬件组件的工作模式；并根据启动顺序找到硬盘上的启动扇区。
>
> 但 BIOS/UEFI 的角色到此为止——它本质上是一个“健康检查员兼调度员”。它可以检查硬件是否健康并决定从哪个设备启动，但不会管理你的文件，运行应用程序，或显示美观的桌面。这些复杂任务需要更强大的软件接管——**操作系统**。
>
> 交接非常具体：BIOS/UEFI 从硬盘的第一个扇区（启动扇区）读取引导程序代码，将其加载到内存，然后指示 CPU 跳转到该代码并开始执行。从这一刻起，控制权正式从固件移交给操作系统引导程序。引导程序将逐步加载操作系统内核，启动系统服务，并最终呈现熟悉的桌面。这个链条中最复杂的一棒已经开始。

## 3. 操作系统启动：从内核到桌面

<OSBootInteractiveDemo />

---

> **第三段中继完成** 操作系统已经完全启动，桌面已显示。让我们回顾这一段完成了什么：引导程序从磁盘读取内核，内核接管了CPU和内存，系统服务依次启动（网络、音频、安全中心……），最后图形界面渲染出桌面。
>
> 此时，操作系统就像一栋水电已接通且物业已入住的建筑——**进程管理**为每个居民（程序）分配房间，**内存管理**分配空间，**文件系统**管理仓库，**网络协议栈**处理外部通信。这些“公共服务”是所有应用运行的基础设施。没有它们，任何程序都无法启动。
>
> 现在你想上网，于是双击桌面上的浏览器图标。在这一简单操作背后，操作系统必须执行一系列任务：找到浏览器的可执行文件在硬盘上的位置，为其创建独立进程，分配内存空间，并加载程序代码……这直接体现了操作系统的“进程管理”能力。接下来，我们来看浏览器是如何启动的。

## 4. 打开浏览器：应用程序启动

### 4.1 应用程序启动过程

当你双击浏览器图标时，操作系统将：

1. **找到可执行文件**：根据文件关联，定位浏览器的 `.exe`（Windows）或可执行文件
2. **创建进程**：为浏览器创建一个新的**进程**
3. **加载程序**：将浏览器的代码从硬盘加载到内存中
4. **初始化**：启动浏览器的主线程、渲染引擎、网络引擎等

```
Browser launch process:
┌─────────────────────────────────────┐
│  1. Double-click icon               │
│  2. OS finds browser executable     │
│  3. Create browser process          │
│  4. Load browser code into memory   │
│  5. Initialize modules (rendering,  │
│     networking, JS engine)          │
│  6. Display browser window          │
└─────────────────────────────────────┘
```

### 4.2 浏览器的主要组成部分

现代浏览器是一个复杂的“操作系统”，主要由以下部分组成：

| 模块 | 功能 |
|-----|------|
| **用户界面** | 地址栏、标签页、书签等 |
| **浏览器引擎** | 协调用户界面与渲染引擎 |
| **渲染引擎** | 解析 HTML/CSS 并显示网页 |
| **JavaScript 引擎** | 执行 JavaScript 代码 |
| **网络模块** | 发送 HTTP 请求 |
| **UI 后端** | 绘制基本 UI 组件 |
| **数据存储** | Cookies、LocalStorage 等 |

<BrowserArchitectureDemo />

---

> **第四棒传递完成** 浏览器已成功启动。操作系统为其创建了独立进程，分配了内存空间，浏览器内部的各模块也已全部初始化：渲染引擎已准备好解析 HTML/CSS，JavaScript 引擎已准备好执行脚本，网络模块已准备好发送和接收数据。
>
> 你可以把此时的浏览器想象成已经启动发动机的汽车——引擎正在运转，仪表盘已点亮，导航系统已准备就绪。但汽车仍然停在原地，因为驾驶员（你）还没有告诉它“去哪里”。浏览器窗口空白，光标在地址栏闪烁，等待你的输入。
>
> 当你在地址栏输入 `https://www.example.com` 并按下回车，一场贯穿整个互联网的旅程就开始了。浏览器的网络模块接管这个请求：首先解析 URL 结构，然后通过 DNS 将域名转换为 IP 地址，与远程服务器建立 TCP 连接，协商加密通道，发送 HTTP 请求，等待服务器响应，最后将接收到的 HTML/CSS/JS 代码传递给渲染引擎以绘制你看到的网页。这一阶段步骤最多，涉及的协议也最丰富——也是 Web 开发者最需要理解的部分。

## 5. 访问 URL：完整的网络请求过程

### 5.1 URL 概述

**URL（统一资源定位符）** 是资源的地址。就像现实世界的地址，它用于定位互联网上的资源。

```
URL structure:
┌─────────────────────────────────────────────────────────┐
│  https://  │  www.example.com  │  /path/to/page  │ ?query=1 │
│  Protocol  │     Domain        │      Path       │  Query   │
└─────────────────────────────────────────────────────────┘
```

- **协议**：如何访问资源（http、https、ftp 等）
- **域名**：服务器的地址
- **路径**：服务器上资源的位置
- **查询**：附加参数

### 5.2 访问 URL 的完整流程

当你访问 `https://www.example.com` 时，发生的情况如下：

<URLRequestDemo />

#### 步骤 1：URL 解析

浏览器首先**解析 URL**，提取协议、域名、路径及其他信息。

```
URL parsing process:
https://www.example.com/index.html
  ↓
Protocol: https
Domain: www.example.com
Path: /index.html
```

#### 步骤 2：DNS解析

计算机通过网络使用**IP地址**（例如 93.184.216.34）访问服务器，而不是使用域名。因此，域名必须转换为IP地址。这个过程称为**DNS解析**。

```
DNS resolution flow:
┌─────────────────────────────────────────────────────────┐
│  Browser cache → hosts file → Local DNS cache → DNS server  │
└─────────────────────────────────────────────────────────┘

Actual process:
1. Browser checks cache (visited recently?)
2. Operating system checks DNS cache
3. Send query request to DNS server
4. DNS server returns IP address
```

#### 第三步：建立 TCP 连接

在获得 IP 地址后，浏览器需要与服务器建立 **TCP 连接**。TCP 是一种传输层协议，用于确保数据传输的可靠性。

```
TCP three-way handshake:
┌─────────────────────────────────────────────────────────┐
│  Client → Server: SYN (synchronization request)         │
│  Server → Client: SYN-ACK (acknowledge and synchronize) │
│  Client → Server: ACK (acknowledgment)                  │
│                        ↓                                │
│  Connection established!                                │
└─────────────────────────────────────────────────────────┘
```

对于 **HTTPS**，还需要进行 **TLS/SSL 握手** 来建立加密通道。

#### 第4步：发送 HTTP 请求

连接建立后，浏览器向服务器发送 **HTTP 请求**：

```
HTTP request format:
┌─────────────────────────────────────────────────────────┐
│  GET /index.html HTTP/1.1                              │
│  Host: www.example.com                                 │
│  User-Agent: Mozilla/5.0...                             │
│  Accept: text/html                                     │
│                                                         │
│  (empty line)                                          │
└─────────────────────────────────────────────────────────┘
```

常用的 HTTP 方法：

| 方法 | 含义 | 目的 |
|-----|------|-----|
| **GET** | 获取资源 | 浏览网页 |
| **POST** | 提交数据 | 登录、表单提交 |
| **PUT** | 上传资源 | 文件上传 |
| **DELETE** | 删除资源 | 数据删除 |

#### 第五步：服务器处理请求

当服务器（通常是 **Web 服务器** 如 Nginx 或 Apache）接收到请求后：

1. **解析请求**：了解客户端的需求
2. **处理业务逻辑**：调用后端程序（如 Python、Node.js、Java）
3. **查询数据库**：检索所需数据
4. **生成响应**：将数据组装成 HTML、JSON 或其他格式

```
Server processing flow:
┌─────────────────────────────────────────────────────────┐
│  1. Web server receives request (Nginx/Apache)          │
│  2. Route to the appropriate handler based on path      │
│  3. Execute backend code (API, business logic)          │
│  4. Query database if needed, retrieve data             │
│  5. Assemble response (HTML/JSON/CSS/JS)               │
│  6. Return HTTP response                                │
└─────────────────────────────────────────────────────────┘
```

#### 第6步：返回HTTP响应

服务器返回一个包含状态码、响应头和响应体的**HTTP响应**：

```
HTTP response format:
┌─────────────────────────────────────────────────────────┐
│  HTTP/1.1 200 OK                                       │
│  Content-Type: text/html                               │
│  Content-Length: 1234                                  │
│                                                         │
│  <!DOCTYPE html>                                       │
│  <html>...</html>                                      │
└─────────────────────────────────────────────────────────┘
```

常见状态码：

| 状态码 | 含义 |
|-------|------|
| **200** | 成功 |
| **301/302** | 重定向 |
| **404** | 资源未找到 |
| **500** | 服务器错误 |

#### 第7步：浏览器渲染页面

收到响应后，浏览器开始**渲染页面**：

<RenderingDemo />

1. **解析 HTML**：构建 DOM 树
2. **解析 CSS**：计算样式并构建渲染树
3. **执行 JavaScript**：运行页面中的 JS 代码
4. **绘制页面**：在屏幕上显示内容

```
Browser rendering process:
┌─────────────────────────────────────────────────────────┐
│  1. HTML parsing → DOM tree                             │
│  2. CSS parsing → Style rules                           │
│  3. DOM + CSS → Render tree                             │
│  4. Layout calculation → Size and position of elements  │
│  5. Paint → Pixels displayed on screen                  │
│  6. Composite → Multiple layers merged for display      │
└─────────────────────────────────────────────────────────┘
```

---

> **最终接力阶段完成** 网页最终显示在你的屏幕上了！让我们回顾一下最后这一阶段经历了多少步骤：浏览器解析 URL 以提取协议和域名，通过分层 DNS 查询将域名翻译为 IP 地址，通过 TCP 三次握手与服务器建立可靠连接，通过 TLS 握手建立加密通道，发送 HTTP 请求，服务器处理业务逻辑，查询数据库，组装响应数据并返回，最后浏览器渲染引擎将 HTML 解析为 DOM 树，将 CSS 计算为样式规则，将两者合并为渲染树，计算布局，并逐像素地绘制到屏幕上。
>
> 现在让我们拉远视角，回顾这场接力赛从头到尾的全貌。从按下电源按钮的那一刻起：电流唤醒硬件（第一棒）→ 固件检查设备并找到启动磁盘（第二棒）→ 操作系统从内核到桌面完全启动（第三棒）→ 浏览器作为应用程序由操作系统启动（第四棒）→ 网络请求穿越互联网获取数据并渲染成页面（第五棒）。五棒首尾相连，每一棒都建立在前一棒的结果之上。如果缺少任何一棒，你都无法在眼前看到网页。
>
> 接下来，让我们用完整的流程图连接这五个阶段，并可视化它们的依赖关系。

让我们连接整个过程：

```
Complete process from pressing power to visiting a website:

┌──────────────────────────────────────────────────────────────────┐
│  1. Press Power                                                   │
│     └── Power startup → Motherboard wake-up → CPU reset → Execute BIOS/UEFI │

│  2. BIOS/UEFI Boot                                                │

```

---

> 看整个链条，你会注意到一个有趣的模式：每个阶段解决的完全不同的问题，涉及的技术领域也截然不同。第一阶段属于**电气工程**领域——电力转换、电路设计、信号传输；第二阶段属于**固件编程**——使用低级代码直接控制硬件；第三阶段是**操作系统**的世界——进程调度、内存管理、文件系统，这些都是计算机科学的核心主题；第四阶段涉及**应用开发**——如何设计复杂的软件架构，比如浏览器；第五阶段涉及**计算机网络**和**前端开发**——从像 DNS、TCP/IP、HTTP 这样的网络协议，到 HTML/CSS/JS 的解析和渲染。
>
> 这也解释了为什么“全栈工程师”需要广泛的知识：你写的每一行前端代码都必须经过整个链条才能到达用户。理解每一个环节能帮助你快速定位问题——是网络层的问题？服务器问题？还是浏览器渲染的问题？
