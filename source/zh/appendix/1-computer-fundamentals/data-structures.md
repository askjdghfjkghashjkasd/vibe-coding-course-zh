# 数据结构：导论

::: 提示 前言
**程序 = 数据结构算法。** 之前，我们了解过CPU如何执行指令，操作系统如何管理资源。但程序处理的核心对象是**数据**——用户信息、产品列表、社交关系......这些数据在内存中的组织方式直接决定了程序是快还是慢。你可能会想：为什么有些程序能快速处理数万条记录，而有些程序只需几百条就会冻结？答案往往在于**数据结构的选择**。
:::

**你会从这篇文章中学到什么？**

完成本章后，你将获得：

- **直觉判断**：当你看到需求时，正确的数据结构会自动浮现在脑海

- **权衡思维**：理解“以空间换时间”与“以时间换空间”——要知道没有完美的数据结构
- **代码读取能力**：HashMap、Stack、Queue等术语将不再是外接的
- **进一步学习的基础**：为数据库索引、缓存系统、搜索引擎及其他技术奠定基础

## 1.大局：数据结构概述

想象你需要整理一堆书：

- **堆在地上**：要找到一本书，你必须一本一本翻阅——这是最原始的储藏方式
- **按编号排列于书架上**：直接前往对应位置取用——这是一个**数组**
- **按类别分类到柜子**：先确定柜子，然后找到书——这是一个**哈希表**
- **按字母顺序排列于多层书架**：每次消除一半——这是一棵**树**

不同的组织方法导致了截然不同的图书检索效率。**数据结构是数据的“组织方法”**——它决定了数据的存储、发现和修改方式。

<DataStructure概览演示 />

所有数据结构都可以分为四大类型：

|类型 |数据关系 |典型示例 |现实生活中的类比 |
|------|---------|---------|---------|
|**线性**一对一，排成一行 |数组、链表、堆栈、队列 |火车车厢，结账线 |
|**哈希** |键→值映射 |哈希表、词典、集合 |图书馆索引卡 |
|**树** |一对多，层级结构 |二叉树，B树，堆 |家谱树，文件夹结构 |
|**图** |多对多，网络化 |有向图，无向图 |地铁图，社交网络 |

::: 提示 为什么要学这么多类型？
因为**没有通用的数据结构**。每一种数据结构都是“查找速度”、“插入速度”和“内存占用”之间的权衡。就像你不会用背包搬家具，或者用卡车送一封信一样——选对工具决定了一切。
:::

## 2.线性结构：最基本的组织

线性结构是最直观的数据组织方式——数据项依次排列，就像火车车厢一样。但不同的“连接方法”和“操作端点”会产生四种变体，每种都有其优势。

<线性结构演示 />

### 2.1 数组与链表：两种根本不同的存储方法

数组和链表是最基本的两种线性结构。它们的核心区别在于**内存布局**：

|比较 |数组 |链表 |
|---------|------|------|
|**内存布局**一个连续的块 |分散，通过指针连接 |
|**访问第n个元素** |直接计算地址，O（1） |逐个从头部搜索，O（n） |
|**插入中间** |必须移动所有后续元素，O（n） |只需更换两个指针，O（1） |
|**尺寸**创建时固定 |可随时增长 |
|**现实生活中的类比**一排编号储物柜 |一串寻宝线索 |

::: 提示 什么时候使用数组？什么时候使用链表？
- **已知数据量，按位置频繁访问** →数组（例如，学生成绩表、像素矩阵）
- **未知数据量，频繁插入/删除** →链表（例如，播放列表、撤销历史）
- **不确定？** → 从数组开始。在大多数情况下，数组的缓存友好性带来更大的性能优势
:::

### 2.2 堆栈与队列：带有“规则”的线性结构

栈和队列本质上是数组或链表，只是带有**受限的操作方法**。这看似功能减少，但这一限制赋予了它们特定的用途：

|结构 |规则 |操作 |类比 |你的代码中哪里？|
|------|------|------|------|-----------------|
|**堆叠** |后进先出（LIFO）|推/弹 |一堆盘子 |功能调用堆栈，浏览器返回按钮，Ctrl Z撤销 |
|**排队** |先进先出（FIFO）|排队/退队 |排队等待工单 |任务调度、消息队列、打印队列 |

::: 提示 为什么“限制”其实是件好事？
想象一个只有两个操作的栈——“放置plate”和“移除plate”。你永远不会弄错顺序。**限制带来确定性，确定性带来可靠性。**函数调用栈依赖“后进先出”原则，确保最近调用的函数先返回。如果允许对中间函数的随机访问，程序将会变得混乱。
:::

## 3.哈希表：最快的查找

线性结构查找速度不够快——数组需要 O（n） 遍历，甚至排序的二分查找也是 O（log n）。有没有结构能实现 **O（1） 次直接查找**？是的——哈希表。

<HashTableDemo />

### 3.1 哈希表的核心思想

哈希表的原理其实相当简单：

1. 你提供一个**密钥**（例如，“apple”）
2. **哈希函数**从密钥计算一个数字（例如，`hash("apple") = 3`）
3. 直接进入数组的第3位——无需穿越，只需一步即可到达

这就像图书馆的索引系统：你不是逐层书架搜索，而是查看索引卡以找到书籍的准确位置。

### 3.2 哈希碰撞解决方法

两个不同的键可能计算出相同的索引——这被称为**哈希碰撞**。就像两本索引号相同的书指向相同的位置。

|解析方法 |原理 |类比 |
|---------|------|------|
|**链式 **使用链表在同一位置存储多个值 |将多本书放进同一个柜子 |
|**开放地址** |如果发生碰撞，寻找下一个空槽 |如果柜子满了，使用相邻的槽 |

### 3.3 哈希表性能

|运算 |平均情况 |最坏情况（所有碰撞） |
|------|---------|-------------------|
|**查找**O（1） |O（n） |
|**插入** |O（1） |O（n） |
|**删除** |O（1） |O（n） |

::: 警告 它什么时候会降解？
当所有键映射到同一索引时，哈希表退化为链表，所有操作变为 O（n）。预防：选择一个好的哈希函数动态调整大小（当负载因子超过阈值时展开）。
:::

::: 提示 哈希表在你的代码中无处不在
- JavaScript `{}` 对象和 `Map` → 哈希表
- Python `dict` → 哈希表
- Java `HashMap` → 哈希表
- 数据库索引 → 也在底层使用哈希

每次你写入 `user["name"]` 或 `map.get("key")`，背后都有哈希表在运行。
:::

## 4.树结构：表达层级关系

哈希表查找速度快，但数据是无序的。如果你需要**既快速查找又需要有序数据**，你需要树结构。

树的核心特征是：每个节点可以有多个“子节点”，但只有一个“父节点”（根节点除外）。这种一对多的层级关系在现实世界中无处不在。

<TreeStructureDemo />

### 4.1 二叉搜索树：有序树

二叉搜索树有一个简单但强大的规则：**左边较小，右边较大**。

- 左子树<根节点的所有值- 右子树>根节点的所有值

在搜索时，每次比较都会消除一半节点，时间复杂度为 O（log n）。就像数字猜测游戏——“它比50大还是小？”“更大。”“大于75还是大？”——每次都去掉一半。

### 4.2 平衡树：防止退化

二叉搜索树存在一个问题：如果数据按顺序插入（1， 2， 3， 4， 5），树会退化成链表，查找返回到O（n）。平衡树通过自动调整结构来避免此问题：

|类型 |平衡策略 |特性 |典型应用 |
|------|---------|------|---------|
|**AVL树** |严格平衡（高度差≤1） |最快查找，稍慢的插入/删除 |需要频繁查找的场景 |
|**红黑树** |近似平衡 |整体性能良好 |Java TreeMap，Linux 内核 |
|**B树** |多路平衡;一个节点存储多个值 |减少磁盘I/O |数据库索引 |

::: 提示 你的代码里树在哪里？
- **文件系统**：嵌套文件夹是树状结构
- **HTML DOM**： `<html>` → `<body>` → `<div>` → `<p>` 是一棵树
- **数据库索引**：B树支持仅3-4次磁盘读取即可跨数百万条记录进行查找
- **JSON/XML**：嵌套数据格式本质上是树
:::

## 5.图结构：复杂关系网络

树只能表示“一对多”的层级关系。但现实世界中许多关系是“多对多”的——你的朋友也有朋友，城市之间有多条路径。一个结构中**任何节点都可能连接到任何其他节点**，这就是图。

<GraphStructureDemo />

### 5.1 三种图类型

|类型 |特征 |类比 |典型应用 |
|------|------|------|---------|
|**无向图** |边无方向;A→B等于B→A |微信好友（互助）|社交网络，通信网络 |
|**有向图** |边有方向;A→B与B→A不同 |微博跟随（单向）|网页链接，依赖关系 |
|**加权图** |边有权重（距离、成本等） |城市间的高速公路（含里程）|地图导航，最短路径 |

### 5.2 图遍历

图遍历比线性结构更复杂，因为可能存在环（A→B→C→A），需要追踪“访问”节点：

|遍历法 |策略 |类比 |用例 |
|---------|------|------|---------|
|**BFS（广度优先）** |先访问所有邻居，然后访问邻居的邻居 |水面中扩散的涟漪 |最短路径，水平阶遍历 |
|**DFS（深度优先）** |尽可能深入一条路径，卡住时回头 |迷宫导航 |路径搜索，连接性检查 |

::: 提示 现实世界中的图表
- **地图导航**：城市是节点，道路是边;导航在图中寻找最短路径
- **社交网络**：用户是节点，关注/友谊是边;“你可能认识的人”是图算法推荐
- **包管理器**：npm/pip 依赖关系为有向图;`npm install` 执行图的拓扑排序
:::

**核心性能比较表：**

|数据结构 |访问 |搜索 |插入 |删除 |空间 |
|---------|------|------|------|------|------|
|**阵列** |O（1） |O（n） |O（n） |O（n） |
|**链表** |O（n） |O（n） |O（1） |O（1） |O（n） |
|**堆栈/排队** |O（n） |O（n） |O（1） |O（n） |
|**哈希表** |— |O（1） |O（1） |O（1） |O（n） |
|**二叉搜索树** |— |O（log n） |O（log n） |O（log n） |O（n） |
|**图表** |— |O（V E） |O（1） |O（E） |O（V E） |

::: 提示 如何阅读此表
- **O（1）**：无论数据量如何，操作时间恒定——最快
- **O（log n）**：数据加倍只增加一步——非常快
- **O（n）**：数据加倍使时间翻倍——平均值
- **O（V E）**：取决于顶点和边的数量——具体针对图

注意：这些都是**平均情况**。最坏情况下，哈希表降级至O（n），二叉搜索树也降级至O（n）。

## 7.选择指南：数据结构应用场景

学了这么多数据结构后，面对实际需求时你该如何选择？关键是**从需求开始**，然后问自己几个问题：

1. **最常用的操作是什么？** 查找？插入？删除？遍历？
2. **数据项之间的关系是什么？** 一对一？一对多？多对多？
3. **数据量有多大？** 面对几十条记录和数百万条记录，最佳选择可能完全不同
4. **顺序重要吗？** 是否需要以特定顺序遍历数据？

<DataStructureSelectorDemo />

**快速决策流程：**

| 你的需求 | 推荐的数据结构 | 原因 |
|---------|---------|------|
| 通过位置快速访问 | 数组 | O(1) 随机访问 |
| 中间位置频繁插入/删除 | 链表 | O(1) 插入/删除无需移动元素 |
| 后进先出（撤销、递归） | 栈 | LIFO 语义自然匹配 |
| 先进先出（任务队列） | 队列 | FIFO 语义自然匹配 |
| 通过键快速查找 | 哈希表 | O(1) 平均查找 |
| 有序数据  快速查找 | 二叉搜索树 | O(log n) 查找，同时保持顺序 |
| 复杂的多对多关系 | 图 | 可以表达任意节点间的连接 |

::: tip 实践中的经验法则
- **80% 的场景** 用数组和哈希表即可
- 当需要顺序时考虑 **树**
- 当关系复杂时考虑 **图**
- **不确定？** 从最简单的开始，遇到性能问题再切换。过早优化是万恶之源
:::

## 总结

> 数据结构是程序的骨架。**数组**像一排编号储物柜——按位置获取项目最快；**链表**像寻宝线索链——插入和删除最灵活；**哈希表**像图书馆索引——按名称查找最快；**树**像家谱树——表示层级关系同时保持顺序；**图**像地铁图——表示任意复杂的网络关系。没有最好的数据结构，只有最合适的——关键是理解每种结构的优缺点，并根据实际需求进行权衡。
