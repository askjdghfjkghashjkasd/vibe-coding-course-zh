# 数据模型：完整概览 — 文档、图、时间序列和向量

::: tip 核心问题
**为什么不能直接把所有数据都塞进 MySQL 表？** 当你的数据是社交网络图、每秒数百万条传感器读数，或者 AI 理解语义所需的向量时，关系型表格就显得力不从心。不同的数据形态需要不同的建模方法。
:::

---

## 1. 超越关系型：需要其他数据模型的动机

关系型数据库（MySQL、PostgreSQL）通过“表   行   列”来组织数据，适合结构化的、定义明确的业务数据。但现实世界的数据形式远不止于此：

| 数据形态 | 关系型缺点 | 更合适的模型 |
|----------|-------------|-------------|
| 用户资料（灵活字段，嵌套结构） | 频繁 ALTER TABLE，大量 NULL 列 | **文档模型** |
| 社交网络（朋友的朋友的朋友） | 多层 JOIN 性能急剧下降 | **图模型** |
| 监控指标（每秒数百万写入） | 写入瓶颈，历史数据膨胀 | **时间序列模型** |
| AI 语义搜索（“相似含义”内容） | 无法表达语义相似性 | **向量模型** |

::: info 核心洞察
这不是要“替换”关系型数据库，而是“补充”它们。大多数系统仍然在 MySQL/PostgreSQL 上运行核心业务，但针对特定场景引入专业的数据模型，可以带来数量级的性能提升。
:::

## 2. 文档模型

### 2.1 文档模型概述

文档模型以 **JSON/BSON 文档** 的形式存储数据，每条记录都是一个自包含的文档，并且可以拥有不同的字段结构。

```json
{
  "_id": "user_1001",
  "name": "Zhang San",
  "tags": ["VIP", "Active"],
  "address": { "city": "Beijing", "district": "Chaoyang" },
  "orders": [
    { "id": "o1", "amount": 299 },
    { "id": "o2", "amount": 599 }
  ]
}
```

**关键特性:**
- **无模式约束**：无需预先定义表结构；字段可以随时添加或删除
- **嵌套结构**：地址和订单直接嵌入文档；一次读取即可获取所有数据
- **水平扩展**：天然适合分片，轻松处理海量数据

### 2.2 文档 vs 关系型

| 比较 | 关系型 (MySQL) | 文档型 (MongoDB) |
|----------|----------------|------------------|
| 数据结构 | 固定模式，修改需用 ALTER TABLE | 灵活模式，可随时添加字段 |
| 嵌套数据 | 需要多表 JOIN | 直接嵌入文档 |
| 跨记录关系 | JOIN 功能强大 | 关系查询较弱 |
| 最适合 | 结构稳定的业务数据 | 结构多变的内容数据 |

### 2.3 典型使用场景

- **CMS 内容管理**：具有不同结构的文章、评论和标签
- **用户资料**：不同用户拥有不同的属性字段
- **产品目录**：手机有“屏幕尺寸”，食品有“保质期”——字段完全不同
- **配置中心**：每个服务的配置结构不一致

::: warning 常见误区
“MongoDB 不需要数据结构设计”——错误！文档模型同样需要仔细设计：嵌套层级不宜过深，频繁更新的子文档应拆分到单独集合。
:::

## 3. 图模型

### 3.1 图模型概述

图模型使用 **节点** 和 **边** 来表示实体及其关系。每个节点是一个实体，每条边是一种关系，节点和边都可以携带属性。

```
(Zhang San) --[follows]--> (Li Si) --[follows]--> (Wang Wu)
   |                                    |
   +--------[purchased]----> (iPhone) <--[purchased]--+
```

### 3.2 图模型的杀手级功能：多跳查询

**场景**：在社交网络中查找“朋友的朋友的朋友”

关系型方法（3级 JOIN）：```sql
SELECT DISTINCT f3.name
FROM friends f1
JOIN friends f2 ON f1.friend_id = f2.user_id
JOIN friends f3 ON f2.friend_id = f3.user_id
WHERE f1.user_id = 1001;
```

图数据库方法（Cypher 查询语言）：```cypher
MATCH (me)-[:FOLLOWS*1..3]->(target)
WHERE me.name = 'Zhang San'
RETURN DISTINCT target.name
```

在关系型方法中，每增加一次跳数就会增加一次 JOIN，从而导致性能呈指数级下降。图数据库通过指针直接遍历关系，因此多跳查询的性能几乎保持不变。

### 3.3 典型使用场景

- **社交网络**：好友推荐、共同关注、影响力传播
- **知识图谱**：实体关系推理（“谁是谁的学生”）
- **欺诈检测**：发现资金循环、关联账户网络
- **推荐系统**：基于用户-产品-标签关系图的推荐

## 4. 时间序列模型

### 4.1 时间序列模型概述

时间序列模型以**时间戳**为主要轴，特别针对“按时间顺序写入，按时间范围查询”的场景进行了优化。

```
timestamp            device      cpu_usage   memory
2024-01-15 10:00:01  server-01   45%         12.3GB
2024-01-15 10:00:02  server-01   67%         12.5GB
2024-01-15 10:00:03  server-01   92%         14.1GB
```

### 4.2 使用 MySQL 存储时间序列数据的动机不足

| 问题 | MySQL | 时间序列数据库 (InfluxDB) |
|------|-------|----------------------|
| 写入速度 | 每秒数万条 | **每秒数百万条** |
| 历史数据 | 手动清理，表持续增长 | **自动过期策略（TTL）** |
| 聚合查询 | GROUP BY 慢 | **内置降采样**（5秒 → 1分钟平均） |
| 存储效率 | 通用存储空间浪费 | **列式压缩**，节省 90% 空间 |

### 4.3 典型使用场景

- **服务器监控**：每秒收集 CPU、内存、磁盘信息
- **物联网传感器**：温度、湿度、GPS 轨迹
- **金融市场**：秒级股票价格与交易量
- **日志分析**：应用日志的时间线聚合

## 5. 向量模型

### 5.1 向量模型概述

向量模型通过 **嵌入模型** 将文本、图像、音频等非结构化数据转化为高维数值向量，然后通过计算向量之间的距离来衡量语义相似度。

```
"delicious Japanese food" → Embedding → [0.82, 0.15, 0.91, 0.33, ...]
                                        ↓ Cosine similarity
"Ginza sushi master"    → [0.80, 0.18, 0.89, ...] → 96% similar
"Italian pizza"          → [0.12, 0.85, 0.20, ...] → 31% similar
```

### 5.2 向量搜索与关键词搜索对比

| 对比 | 关键词搜索（LIKE / 全文索引） | 向量搜索 |
|------|---------------------------|---------|
| 搜索方法 | 精确字符串匹配 | 语义相似度匹配 |
| "delicious Japanese food" | 只能匹配包含“Japanese food”的文本 | 可以找到“寿司”、“刺身”、“居酒屋” |
| 多语言 | 需要单独处理 | 跨语言语义理解 |
| 多模态 | 仅文本 | 文本、图像和音频统一检索 |

### 5.3 典型使用场景

- **RAG（检索增强生成）**：为大语言模型提供相关知识片段
- **语义搜索**：理解用户意图而非关键词
- **图片搜索**：上传图片以查找视觉相似的图片
- **推荐系统**：基于内容语义的相似性推荐

::: tip 选择向量数据库
- **独立向量数据库**：Pinecone、Milvus、Weaviate — 专注于向量检索，性能最佳
- **传统数据库扩展**：pgvector（PostgreSQL）、Atlas Vector Search（MongoDB） — 减少架构复杂性
- **内存向量库**：FAISS、Annoy — 适用于小规模、低延迟场景
:::

## 6. 选择指南：数据模型选择方法

| 数据形态 | 推荐模型 | 代表产品 |
|-------------------|---------|---------|
| 固定结构、关系清晰（订单、用户） | 关系型 | MySQL, PostgreSQL |
| 结构灵活、深度嵌套（内容、配置） | 文档型 | MongoDB, DynamoDB |
| 实体之间关系复杂、需多跳遍历 | 图数据库 | Neo4j, Amazon Neptune |
| 按时间顺序写入，按时间范围查询 | 时序型 | InfluxDB, TimescaleDB |
| 非结构化数据、需基于语义相似度搜索 | 向量型 | Pinecone, Milvus, pgvector |

::: info 实用建议
现代系统通常**多模型结合使用**：
- **核心业务**在PostgreSQL（关系型）
- **用户行为日志**在InfluxDB（时序型）
- **AI知识库**在Milvus或pgvector（向量型）
- **推荐引擎**在Neo4j（图数据库）

不要尝试寻找“一个数据库解决所有问题” —— 相反，应让每种数据找到最适合的存放环境。
:::
