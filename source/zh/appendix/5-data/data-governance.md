## 0. 全景视角：为何需要数据治理

数据治理不是一个技术问题——它是一个**管理问题**。它回答核心问题：**谁负责数据？数据标准是什么？我们如何确保数据保持可信？**

想象一家有100张数据表的公司，每张表由不同的团队维护，缺乏统一的命名规范，没有数据字典，也没有质量检查。结果：同一个“月活跃用户”指标，营销部门得出500万，产品部门得出300万——因为定义不同。

::: tip 数据治理的四大支柱
1. **组织**：明确数据负责人和数据管理员的角色与职责
2. **流程**：建立数据入库、变更和下线的标准流程
3. **技术**：部署数据质量监控、元数据管理、血缘追踪等工具
4. **文化**：让全公司认识到“数据是资产”，而非“数据是副产品”
:::

## 1. 数据质量的六个维度

数据质量不是一个模糊的概念——它可以通过六个具体维度进行衡量。每个维度都有清晰的定义和检测方法。

<DataQualityDemo />

| 维度 | 定义 | 检测方法 | 常见问题 |
|------|------|---------|---------|
| 完整性 | 数据是否有缺失值 | 空值率检查 | 必填字段为空，相关数据缺失 |
| 准确性 | 数据是否正确 | 规则验证，抽样核查 | 负数金额，日期无效 |
| 一致性 | 多源数据是否匹配 | 跨系统对比 | CRM 和订单系统用户名不一致 |
| 时效性 | 数据是否及时更新 | 更新时间检查 | 库存数据滞后，价格未同步 |
| 唯一性 | 是否存在重复记录 | 去重检查 | 同一用户重复注册 |
| 有效性 | 数据是否符合格式规则 | 正则/范围验证 | 邮箱格式无效，年龄为负 |

::: tip 数据质量的 1-10-100 法则
- **$1**：在数据录入点验证数据，防止脏数据进入
- **$10**：清洗数据仓库中已有的脏数据
- **$100**：脏数据导致决策错误的损失

越早发现并修复数据质量问题，成本越低。
:::

## 2. 数据治理框架：全生命周期管理

数据治理不是一次性项目，而是贯穿整个数据生命周期的持续过程。从数据创建到销毁，每个阶段都需要明确标准和责任人。

<DataGovernanceFrameworkDemo />

| 阶段 | 核心产出 | 关键角色 |
|------|---------|---------|
| 定义标准 | 数据字典、命名规范、分类及分级标准 | 数据架构师 |
| 数据接入 | 入库标准、验证规则、血缘记录 | 数据工程师 |
| 存储管理 | 分层模型、权限矩阵、生命周期策略 | DBA / 平台工程师 |
| 数据使用 | 数据目录、脱敏规则、质量报告 | 数据分析师 / 业务负责人 |
| 归档与销毁 | 归档策略、删除记录、审计日志 | 安全与合规团队 |

## 2. 数据治理框架

数据治理不能仅靠购买工具来解决——它需要完整的框架。行业中最常用的参考框架是 DAMA-DMBOK（数据管理知识体系）。

| 治理领域 | 核心内容 | 关键产出 |
|---------|---------|---------|
| 数据架构 | 定义数据模型、数据流、存储策略 | 数据架构图，ER 图 |
| 数据标准 | 统一命名规范、编码标准、指标定义 | 数据字典，指标库 |
| 数据质量 | 建立质量规则、监控报警、整改流程 | 质量报告，SLA 仪表盘 |
| 数据安全 | 分类分级、访问控制、脱敏及加密 | 安全策略，审计日志 |
| 主数据管理 | 核心实体（如客户和产品）的统一“金字塔记录” | 主数据中心 |
| 数据生命周期 | 管理从数据创建到归档销毁的全流程 | 保留策略，归档规则 |

::: 提示 数据治理成熟度模型
- **一级 - 初始**：没有统一标准，每个团队独立运作
- **二级 - 可重复**：存在基本文档，但执行不一致
- **三级 - 已定义**：存在统一的治理流程和工具，大部分团队遵循
- **四级 - 可管理**：具备量化的质量指标和自动化监控
- **五级 - 持续优化**：持续改进，将数据治理集成到日常开发工作流中
:::

## 3. 数据血缘：来源与去向

数据血缘记录数据从来源到最终使用的完整流向路径。它像数据的“家谱”，让你能够追溯任何数据的来源和去向。

<DataLineageDemo />

数据血缘在实际中有三个核心应用场景：

| 场景 | 问题 | 血缘如何帮助 |
|------|------|------------|
| 影响分析 | 如果我修改用户表中的某个字段，下游哪些报表会受到影响？ | 沿着血缘追踪所有下游依赖 |
| 根因调查 | 今天的GMV报表数据异常——问题出在哪里？ | 沿着血缘向上追踪每一步 |
| 合规审计 | 用户的手机号经过了哪些系统？是否在各处进行脱敏？ | 追踪敏感字段的完整链路 |

::: 提示 血缘收集的两种方法
- **主动收集**：解析SQL语句和ETL配置，自动抽取表级和字段级血缘关系
- **被动收集**：通过hook拦截查询引擎（如Hive、Spark）的执行计划，实时记录血缘

主流工具如Apache Atlas、DataHub和OpenLineage都支持自动化血缘收集。
:::

## 4. 元数据管理：“关于数据的数据”

元数据是关于数据的数据。如果数据是一本书的内容，元数据就是书的目录、作者、出版日期和ISBN号。没有元数据，数据只是堆积的无法理解的数字和字符串。

| 元数据类型 | 描述 | 示例 |
|-----------|------|------|
| 技术元数据 | 关于数据的物理存储信息 | 表名、字段类型、分区方式、存储位置 |
| 业务元数据 | 数据的业务含义 | 字段显示名称、业务定义、计算方法 |
| 操作元数据 | 数据的运行状态 | ETL执行时间、数据量、更新频率 |

::: 提示 数据字典的重要性
数据字典是元数据管理最基础的产出。好的数据字典应该包括：
- **字段名**：英文名和显示名
- **数据类型**：VARCHAR(50)、INT、DATETIME等
- **业务定义**：此字段代表什么？如何计算？
- **取值范围**：有效值有哪些？是否允许为空？
- **负责人**：谁维护此字段？出现问题联系谁？

没有数据字典，新成员可能需要一周才能理解一个表的含义；有了数据字典，10分钟即可。
:::

## 5. 数据分层架构：ODS → DWD → DWS → ADS

数据仓库并不是将所有数据堆在一起，而是根据**处理程度**将数据分层存储。每一层有明确责任，上层依赖下层，逐步将原始数据精炼成可用于业务的数据。

|层 |全名 |责任 |数据特征 |
|------|------|------|---------|
|ODS |运营数据存储 |按现状同步业务数据库 |最原始、未处理 |
|DWD |数据仓库详细 |清洁、标准化、去重 |干净的详细信息记录 |
|DWS |数据仓库摘要 |按主题汇总（日/周/月）|预计算汇总指标 |
|ADS |应用数据存储 |面向特定报表/API |直接可用的结果数据 |

::: 提示 为什么要分层？
- **重复使用**：DWD层清理一次，并由所有上层共享，避免重复清理
- **解耦**：业务数据库模式的更改仅影响ODS层，不影响报告
- **性能**：DWS层预聚合;报告可直接读取，无需实时计算
- **可追溯性**：每一层都被保留;问题可以逐层调查
:::

## 6.治理工具与实践

|工具 |定位 |核心能力 |用例 |
|------|------|---------|---------|
|远大期望 |数据质量 |声明式数据验证规则，自动生成质量报告 |Python 数据管道 |
|数据库分析 |数据转换 |SQL建模开发、内置测试与文档生成 |数据仓库建模 |
|DataHub |元数据管理 |数据目录、血统追踪、数据发现 |企业数据治理 |
|Apache 地图集 |元数据管理 |Hadoop 生态系统谱系追踪 |大数据平台 |
|开放元数据 |元数据管理 |开源数据目录，支持多数据源 |中小型团队 |
|Amundsen |数据发现 |基于搜索的数据发现平台 |数据民主化 |

::: 从零开始的治理路径提示
如果您的团队尚未具备数据治理，我们建议按照以下顺序进行：
1. **先建立数据字典**：记录现有表格和字段的含义（即使使用Excel）
2. **添加质量检查**：在关键数据管道中插入基本的空和范围验证
3. **统一指标定义**：标准化核心指标如“DAU”、“MAU”和“GMV”的计算方法
4. **引入工具**：当手动管理变得过于昂贵时，采用像DataHub或dbt这样的工具
5. **建立流程**：数据变更需要审核;质量问题有SLA和警示
:::

## 摘要

数据治理是一种系统化的工程，将数据从“可用”转变为“易用、可信赖且可追溯”。这不是一个一次性项目，而是一个持续的运营过程。

本章的主要收获：

1. **六大质量维度**：完整性、准确性、一致性、及时性、独特性、有效性
2. **四大治理支柱**：组织、流程、技术、文化——皆不可或缺
3. **数据沿革**：跟踪数据的起点和目的地，支持影响分析和根本原因调查
4. **元数据管理**：数据字典是最基础且重要的治理输出
5. **分层架构**：ODS→DWD→DWS→ADS，逐步优化数据价值
6. **增量实施**：从数据词典开始，逐步引入工具和流程
