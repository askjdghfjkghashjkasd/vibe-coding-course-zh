# 请求流程全景

::: tip 介绍
**当你在浏览器中输入 URL 并按下回车键时，网页显示前到底发生了什么？** 这是一个经典的面试问题，更重要的是，它是理解整个 Web 架构的关键。理解这一链条能让你看到前端、后端、网络和数据库如何协同工作。
:::

**你将在本文中学到什么？**

阅读本章后，你将获得：

- **全链路视角**：了解从发送到返回的完整 HTTP 请求过程  
- **逐层职责认知**：知道 DNS、TCP、负载均衡、Web 服务器、应用服务器和数据库各自的作用  
- **问题诊断能力**：知道请求慢或失败时应从哪一层开始排查  
- **性能优化思维**：每一层都有优化潜力；知道优化点在哪里

## 0. 大局观：请求经历了什么

用一个类比来理解：你在网上订购一本书。这个过程和 HTTP 请求非常相似。

| 请求阶段 | 订书的类比 | 技术对应 |
|---------|---------|---------|
| 输入 URL | 你说“我想去那家书店” | 浏览器解析 URL |
| DNS 解析 | 查看地图找到书店地址 | 域名 → IP 地址 |
| TCP 连接 | 走到书店门口，推开门 | 三次握手建立连接 |
| 发送请求 | 告诉店员“我要那本书 'xxx'” | HTTP 请求消息 |
| 服务器处理 | 店员去仓库找书，检查库存，计算价格 | 应用逻辑 数据库查询 |
| 返回响应 | 店员把书交给你 | HTTP 响应消息 |
| 浏览器渲染 | 你打开书开始阅读 | HTML/CSS/JS 解析与渲染 |

## 1. 浏览器发起请求

### 1.1 URL 解析

当你输入 `https://api.example.com/books?id=123` 时，浏览器会将其拆分为几个部分：

| 部分 | 值 | 含义 |
|-----|-----|------|
| 协议 | `https` | 加密通信 |
| 域名 | `api.example.com` | 服务器的“名字” |
| 路径 | `/books` | 要访问的资源 |
| 查询参数 | `id=123` | 额外条件 |

### 1.2 DNS 解析：域名 → IP 地址

计算机无法理解域名；它们只理解 IP 地址（如 `93.184.216.34`）。DNS 是互联网的“电话簿”。

```
Browser cache → System cache → Router cache → ISP DNS → Root name server
     ↓ Hit = use directly; miss = check next level
```

::: 提示 DNS 缓存的重要性
如果每个请求都必须从根名称服务器查询，全球互联网将被 DNS 查询淹没。这就是为什么每一层都有缓存；大多数请求可以在浏览器或系统级别解决。
:::

### 1.3 TCP 三次握手

在找到 IP 地址后，浏览器需要与服务器“建立连接”。TCP 使用三次握手来确保双方都已准备好：

```
Client → Server: Hello, I'd like to connect (SYN)
Server → Client: OK, I'm ready (SYN + ACK)
Client → Server: Received, let's start communicating (ACK)
```

如果使用 HTTPS，则需要额外的 TLS 握手来协商加密。

### 1.4 发送 HTTP 请求

连接建立后，浏览器发送 HTTP 请求消息：

```http
GET /books?id=123 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGci...
User-Agent: Chrome/120.0
```

| 组件 | 内容 |
|---------|------|
| 请求行 | 方法（GET）   路径   协议版本 |
| 请求头 | 元数据：认证、预期数据格式等 |
| 请求体 | 仅用于 POST/PUT 请求；承载要提交的数据 |

## 2. 网络传输：路上的请求

### 2.1 路由与转发

离开你的计算机后，请求会经过多个路由器进行转发，就像一个包裹经过多个中转站一样：

```
Your computer → Home router → ISP network → Backbone network → Target data center
```

每个路由器根据 IP 地址决定“下一跳”。你可以使用 `traceroute` 命令查看请求经过哪些节点。

### 2.2 CDN 加速

如果目标网站使用 CDN（内容分发网络），请求可能不需要到达源服务器：

| 场景 | 路由 |
|-----|------|
| 请求静态资源（图片、CSS、JS） | 由 CDN 边缘节点直接返回 |
| 请求动态数据（API） | 经过 CDN，达到源服务器 |

CDN 的本质是“尽可能将内容预先放置在离用户最近的地方”。

### 2.3 负载均衡

大型网站不只有一台服务器。负载均衡器将请求分配到多台服务器上：

```
User requests → Load balancer → Server A (30% traffic)
                              → Server B (30% traffic)
                              → Server C (40% traffic)
```

常见的分发策略：

| 策略 | 原则 | 使用场景 |
|-----|------|---------|
| 轮询 (Round robin) | 顺序分配 | 配置相同的服务器 |
| 加权轮询 (Weighted round robin) | 按权重分配 | 配置不同的服务器 |
| IP 哈希 (IP hash) | 相同用户 → 相同服务器 | 需要会话保持时 |
| 最少连接 (Least connections) | 分配给连接数最少的服务器 | 当请求处理时间差异较大时 |

## 3. 服务器处理：厨房中的流程

当请求到达服务器后，它会经过多层处理。

### 3.1 网页服务器 (Nginx / Apache)

最先接收请求的通常是网页服务器，其负责：

| 职责 | 描述 |
|-----|------|
| 静态文件服务 | 直接返回 HTML、CSS、JS、图片 |
| 反向代理 | 将 API 请求转发到后端应用 |
| SSL 终止 | 处理 HTTPS 加密/解密 |
| 请求过滤 | 阻止恶意请求，限流 |

### 3.2 应用服务器处理

网页服务器将请求转发到应用服务器 (Node.js、Spring、Django 等)。处理流程：

```
Request enters → Middleware chain → Route matching → Controller → Service layer → Data access layer
```

**中间件的作用:**

1. 解析请求体（JSON、表单数据）
2. 验证身份（检查令牌）
3. 检查权限（该用户能否访问此端点？）
4. 日志记录（谁在什么时候访问了什么）

### 3.3 数据库查询

大多数请求最终都需要与数据库进行交互：

```
Application code: SELECT * FROM books WHERE id = 123
    ↓
Database engine: Parse SQL → Query optimization → Execution plan → Read data
    ↓
Return result: { id: 123, title: "xxx", price: 59.9 }
```

::: 提示 数据库是最常见的性能瓶颈
网络传输通常是毫秒级的，应用逻辑也很快，但未建立索引的数据库查询可能需要几秒甚至几十秒。因此，“慢请求”最有可能是由慢数据库查询引起的。
:::

## 4. 响应返回：数据的回程

### 4.1 构建 HTTP 响应

处理完成后，服务器构建响应消息：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Encoding: gzip
Cache-Control: max-age=3600

{"id": 123, "title": "xxx", "price": 59.9}
```

| 组件 | 内容 |
|---------|------|
| 状态行 | 协议版本   状态码（200 成功，404 未找到，500 服务器错误） |
| 响应头 | 数据格式、缓存策略、压缩方法等 |
| 响应体 | 实际数据内容（JSON、HTML 等） |

### 4.2 数据压缩

服务器通常使用 gzip 或 brotli 压缩响应体以减少传输大小：

| 压缩算法 | 压缩比 | 速度 |
|---------|--------|------|
| gzip | ~70% | 快 |
| brotli | ~80% | 较慢但压缩更好 |

一个 100KB 的 JSON 文件压缩后可能仅为 20-30KB。

### 4.3 浏览器渲染

浏览器接收到响应后：

1. **解析 HTML** → 构建 DOM 树
2. **解析 CSS** → 构建样式树
3. **合并** → 生成渲染树
4. **布局** → 计算每个元素的位置和大小
5. **绘制** → 将像素绘制到屏幕上

## 5. 全链路优化：每一层都可以更快

### 5.1 各层优化方法

| 层 | 优化方法 | 效果 |
|-----|---------|---------|
| DNS | DNS 预取、使用快速 DNS 服务 | 减少 DNS 查询时间 |
| 网络 | CDN、HTTP/2、连接重用 | 减少传输延迟 |
| 服务器 | 缓存（Redis）、异步处理 | 减少处理时间 |
| 数据库 | 索引、查询优化、读写分离 | 减少查询时间 |
| 前端 | 懒加载、代码拆分、资源压缩 | 减少渲染时间 |

### 5.2 缓存：最有效的优化

缓存存在于请求链的每一层：

```
Browser cache → CDN cache → Reverse proxy cache → Application cache (Redis) → Database cache
```

::: tip 缓存的本质
以空间换时间。存储计算结果，下次可以直接使用，无需重新计算。缓存命中率每提高10%，系统性能就能成倍提升。
:::

### 5.3 请求失败时的故障排查

| 症状 | 可能问题层 | 调查方法 |
|-----|------------|---------|
| 完全没有响应 | DNS / 网络 | ping, nslookup |
| 连接超时 | 网络 / 服务器宕机 | telnet, curl |
| 返回4xx | 客户端请求错误 | 检查URL、参数、词元 |
| 返回5xx | 服务器内部错误 | 检查服务器日志 |
| 响应缓慢 | 数据库 / 应用逻辑 | 检查慢查询日志、APM工具 |

---

## 6. 总结

HTTP请求的完整流程：

1. **浏览器**：解析URL → DNS查询 → TCP连接 → 发送请求
2. **网络**：路由转发 → CDN检查 → 负载均衡分配
3. **服务器**：Web服务器接收 → 中间件处理 → 业务逻辑 → 数据库查询
4. **返回**：构建响应 → 压缩 → 网络传输 → 浏览器渲染

::: tip 了解完整链路的价值
当你能在脑海中绘制完整的请求链时，无论遇到什么问题，都能快速定位到是哪一层出了问题。这是从“初级开发者”迈向“能够独立排查问题的人”的关键跃升。
:::
