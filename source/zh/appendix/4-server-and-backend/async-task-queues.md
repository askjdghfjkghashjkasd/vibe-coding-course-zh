## 0.大局观：我们不让用户“等着”的动机

想象一下去餐厅点餐。一家好餐厅在你点完餐后会给你一个订单号，然后你可以找个座位，玩手机，等食物准备好再回来。他们不会让你站在柜台前看厨师做整道菜。

Web应用有许多类似的“烹饪”操作：

- **发送电子邮件/短信**：调用第三方API，可能需要几秒钟
- **生成报告/PDF**：大量数据计算，可能需要数十秒
- **图像/视频处理**：压缩、转码、水印，可能需要几分钟
- **数据同步**：跨系统数据同步，持续时间不可预测

::: 提示 异步任务的核心理念
将耗时的操作从主“请求-响应”流程中剔除，置于后台队列中进行异步处理。用户提交请求后，立即收到“已收到，正在处理”的响应。处理完成后，结果通过通知、轮询或WebSocket传递。
:::

## 1.同步与异步：一个关于订单的故事

当用户提交订单时，后台需要做很多事情：扣除库存、创建订单记录、发送确认邮件、更新推荐系统、记录审计日志......

在同步模式下，这些操作顺序执行——用户必须等待所有操作完成后才能看到结果。在异步模式下，只有核心操作（扣除库存、创建订单）需要立即完成;其余操作被放入队列中进行后台处理。

<AsyncTaskFlowDemo />

| 比较 | 同步处理 | 异步处理 |
|---------|---------|---------|
| 用户等待时间 | 所有操作时长之和 | 仅核心操作时长 |
| 系统吞吐量 | 低（线程被阻塞） | 高（线程快速释放） |
| 失败影响 | 非核心失败会导致整体失败 | 非核心失败不影响主流程 |
| 实现复杂度 | 简单 | 需要额外的队列基础设施 |
| 数据一致性 | 强一致性 | 最终一致性 |

::: tip 何时使用异步？
三个标准：**耗时**（超过1-2秒）、**非核心**（失败不应影响主流程）、**可延迟**（结果不需立即获取）。如果满足其中任意两条，就应考虑使用异步。
:::

## 2. 生产者-消费者模型：任务“装配线”

异步任务队列的核心是经典的**生产者-消费者模式**。该模式有三个角色：

- **生产者**：生成任务的一方，通常是处理用户请求的 Web 服务器
- **队列**：存储待处理任务的缓冲区，通常使用 Redis、RabbitMQ 等实现
- **消费者/工作者**：从队列中取任务并执行的工作进程

<TaskWorkerDemo />

::: tip 队列的三个关键价值
1. **解耦**：生产者不需要知道是谁处理任务；消费者不需要知道任务来自哪里
2. **削峰填谷**：在流量高峰时，任务先堆积在队列中；消费者按自身节奏处理
3. **可靠性**：任务持久化存储在队列中，即使消费者崩溃，任务也不会丢失
:::

| 组件 | 职责 | 常用实现 |
|------|------|---------|
| 消息代理 | 存储和转发任务消息 | Redis, RabbitMQ, Kafka |
| 序列化器 | 序列化/反序列化任务参数 | JSON, MessagePack, Pickle |
| 调度器 | 管理定时与延迟任务 | Cron, APScheduler, node-cron |
| 结果存储 | 保存任务执行结果 | Redis, 数据库, S3 |

## 3. 可靠性保障：任务不能“丢失”或“重复”

在分布式环境中，网络抖动、服务重启和资源紧张随时可能发生。异步任务系统必须具备强可靠性的机制。

两个最关键的问题：**任务丢失**（消费者处理过程中崩溃）和 **任务重复执行**（任务被投递两次）。

<TaskRetryDemo />

::: tip 可靠性的三大支柱
1. **ACK机制**：消费者只有在完成任务后才发送确认（ACK）；未确认的任务将被重新投递
2. **重试策略**：失败任务按策略重试；指数退避加抖动是最佳实践
3. **幂等设计**：多次执行同一任务与执行一次结果相同，通过唯一ID去重实现
:::

| 机制 | 解决的问题 | 实现方式 |
|------|-----------|---------|
| ACK 确认 | 任务丢失 | 处理后手动确认；在超时内未确认的任务会被重新投递 |
| 死信队列 (DLQ) | 反复失败的“毒性消息” | 超过重试次数的任务会被移入 DLQ 以便人工干预 |
| 幂等性 | 重复执行 | 使用唯一任务 ID 进行去重，数据库唯一约束 |
| 优先队列 | 任务饿死 | 优先处理高优先级任务，防止低优先级任务阻塞 |
| 超时控制 | 卡住的任务 | 设置最大执行时间；超时自动终止并重试 |

## 4. 框架选择：选择合适的工具

不同语言生态下有不同的异步任务框架，每个框架在功能丰富性、性能和易用性上有所侧重。选择框架时，首先考虑你的技术栈，然后根据项目规模和需求进行选择。

<AsyncComparisonDemo />

::: tip 选择建议
- **Python 项目**：中大型项目使用 Celery，小型项目使用 RQ
- **Node.js 项目**：BullMQ（Bull 的新一代）是首选
- **Ruby 项目**：Sidekiq 基本上是唯一选择
- **Java 项目**：Spring 生态下使用 Spring Batch，高吞吐量场景使用 Kafka Streams
- **Go 项目**：Asynq（基于 Redis）或 Machinery

如果项目已经在使用 Redis，那么基于 Redis 的方案（Celery Redis、BullMQ、Sidekiq）是最容易上手的。
:::

## 总结

异步任务队列是后端架构中不可或缺的基础设施。它们让系统能够优雅地处理耗时操作，提升用户体验的同时增加系统吞吐量。

本章关键要点：

1. **异步的判断标准**：耗时、非核心、可延迟——满足三项中的两项就应异步处理
2. **生产者-消费者模型**：生产者 → 队列 → 消费者，三个解耦组件协同工作
3. **Worker 池**：多个 Worker 并行消费，提升处理能力
4. **可靠性保障**：ACK 确认 + 重试策略 + 幂等性——三者缺一不可
5. **框架选择**：根据技术栈和项目规模选择；Redis 是最常用的消息中间件
