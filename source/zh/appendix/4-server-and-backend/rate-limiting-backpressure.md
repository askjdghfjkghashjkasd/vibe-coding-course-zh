# 限流与反压原理

::: tip 介绍
**双11零点，数亿用户同时涌入——服务器能承受吗？** 每个系统都有处理能力上限。当请求量超过系统承受能力时，如果不加控制，结果就是没有人能使用服务。限流与反压是保护系统不被“压垮”的两道防线。
:::

## 0. 全局视角：为何要“拒绝”用户

这听起来违反直觉——难道不应该为每个用户提供良好服务吗？但现实是：**如果不拒绝部分请求，所有请求都会失败。**

想象一家只能容纳100人的餐厅，突然涌入1000人。如果不进行限流，结果不是所有人都能就餐，而是厨房崩溃，服务员忙不过来，没人吃到饭。正确的方法是排队，在门口限制入场，先让100人进入，其余等待。

::: tip 限流核心目标
- **保护系统**：防止过载导致服务完全不可用
- **公平分配**：确保被接受的请求可以正常处理
- **优雅降级**：限流的请求返回清晰的429状态码，而不是超时或500错误
:::

## 1. 限流算法：三种经典方法

限流的核心问题是：**在单位时间内，允许通过的最大请求数是多少？** 不同算法在精确度、突发流量处理能力和实现复杂度上有不同权衡。

<RateLimitAlgorithmDemo />

| 算法 | 原理 | 突发流量 | 精确度 | 实现复杂度 |
|------|------|---------|--------|-----------|
| 令牌桶 | 以固定速率增加令牌；请求消耗令牌 | 允许（当桶内有余量时） | 高 | 中 |
| 漏桶 | 请求排队；以固定速率处理 | 不允许（完全平滑） | 高 | 中 |
| 滑动窗口 | 统计时间窗口内的请求数 | 部分允许 | 较高 | 低 |
| 固定窗口 | 按固定时间窗口统计 | 边界可能出现突发 | 低 | 最低 |

::: 提示 选择哪个算法？
- **API 速率限制**：令牌桶最常用，允许合理的突发流量
- **流量整形**：泄漏桶适用于需要恒定输出率的场景
- **简单计数**：滑动窗口易于实现，适用于大多数网页应用
:::

## 2.背压控制：当上游速度快于下游时

速率限制解决了“外部请求过多”的问题，而**背压**则解决了“内部元件速度不匹配”的问题。

当生产者生成数据的速度超过消费者处理速度时，中间缓冲区会不断增长，最终导致内存溢出或数据丢失。反压机制允许消费者“通知上游减速”。

<BackpressureDemo />

::: 小贴士 四种反压策略
1. **丢弃**：缓冲区满时丢弃新旧数据;适用于实时需求高但数据丢失可接受的场景
2. **Block**：暂停生产者，直到用户完成处理;适用于数据无法丢失的场景
3. **采样**：仅处理部分数据;适合高频数据流
4. **弹性扩展**：动态增加用户数量;适合云原生环境
:::

## 3.多层速率限制架构

在生产环境中，单点速率限制是不够的——你需要**多层保护**，每一层解决问题的粒度不同。

|图层 |位置 |速率限制粒度 |工具 |
|------|------|---------|------|
|客户端 |前端/应用 |按钮去跳，请求限速 |lodash.throttle，去跳 |
|CDN/WAF |边缘节点 |IP级，区域级 |Cloudflare速率限制 |
|API网关 |入口网关 |路由级，用户级 |Nginx limit_req，Kong |
|服务器端 |内部应用 |界面层，资源层 |哨兵，Resilience4j |
|数据库 |存储层 |连接计数，QPS |连接池配置，查询电路中断缓慢 |

::: 提示 HTTP 速率限制规范
速率限制请求应返回 `429 Too Many Requests`@ 状态码，响应头包括：
- `Retry-After`：客户端应等待多久再重试（秒数或日期）
- `X-RateLimit-Limit`：费率上限
- `X-RateLimit-Remaining`：剩余配额
- `X-RateLimit-Reset`：配额重置时间
:::

## 摘要

速率限制和背压是保护系统稳定性的两道关键防线。速率限制控制外部流量的速率，而背压则协调内部组件的处理速度。

本章的主要收获：

1. **限流的必要性**：如果不拒绝部分请求，所有请求都会失败
2. **三大核心算法**：令牌桶（允许突发）、漏桶（完全平滑）、滑动窗口（简单且精确）
3. **反压机制**：四种策略——丢弃、阻塞、抽样、扩展
4. **多层保护**：从客户端到数据库，每一层解决不同粒度的问题
5. **429 规范**：被限流时返回标准状态码和限流头信息
