# 负载均衡与网关原理
::: tip 🎯 核心问题
**当单台服务器无法承载负载时，如何“智能地”将流量分配到多台服务器实例上？** 负载均衡是现代分布式系统的“调度器”。本文通过现实生活中的类比（奶茶店结账、包裹分拣、交通控制），深入探讨负载均衡的设计理念与工程实践。
:::

---

## 1. “负载均衡”的动机

### 1.1 一个真实案例：网站架构的演进

一家初创公司在用户快速增长时遇到了严重的性能问题：

**场景：**

```
Phase 1: Single Server
Users → Server (1 vCPU, 2 GB RAM)
       ↓
  1,000 DAU → Peak: 1,000 concurrent users
       ↓
  Problem: CPU at 100%, slow responses, frequent crashes
```

::: 警告 ⚠️ 单服务器的致命缺陷

- **性能瓶颈**：CPU 达到 100%，响应时间 > 5 秒
- **单点故障**：如果服务器宕机，整个网站将无法访问
- **扩展困难**：只能进行纵向扩展（增加 CPU、内存），成本高且有限
  :::

**改进架构（带负载均衡）：**

```
Phase 2: Multiple Servers + Load Balancer
Users → Load Balancer (Nginx)
       ↓
     ├→ Server 1 (1 vCPU, 2 GB RAM)
     ├→ Server 2 (1 vCPU, 2 GB RAM)
     └→ Server 3 (1 vCPU, 2 GB RAM)
```

::: 提示 ✨ 改进

- **性能更好**：3台服务器并行处理，响应时间 < 1 秒
- **高可用性**：如果一台服务器故障，其他服务器继续提供服务
- **横向扩展**：需要更多容量？只需添加更多服务器
:::

### 1.2 通俗理解负载均衡

**珍珠奶茶店柜台**

想象你经营一家受欢迎的珍珠奶茶店：

- **1个柜台**：顾客排队，排在后面的顾客不耐烦，负面评价随之而来
- **3个柜台**：员工将顾客引导到不同柜台，效率提升三倍

**负载均衡器就是“柜台分配员”**：

- **用户**（顾客） → 发出请求
- **负载均衡器**（分配员） → 将请求分配到不同服务器
- **服务器**（柜台） → 处理请求

## 2. 负载均衡概述

### 2.1 第4层负载均衡（L4）：只看地址

**在传输层（TCP/UDP）操作** —— 就像一个送货员只看你的**地址（IP 端口）**，而不关心你是谁或做什么。

**特点：**

- **极快**：简单地址转发，无需解析数据包内容
- **使用场景**：数据库连接、Redis 缓存、长连接游戏服务器
- **代表产品**：LVS（Linux 虚拟服务器）、AWS NLB、Azure 负载均衡器

::: details 工作原理

```
Client request → L4 Load Balancer → Backend server
                    ↓
           Only looks at IP + Port
                    ↓
           Fast forwarding (no content inspection)
```

:::

### 2.2 第7层负载均衡（L7）：检查构建工件内容

**在应用层（HTTP/HTTPS）操作** — 就像一个送货员，不仅检查地址，还会**打开包裹检查其内容**，然后决定如何投递。

**特征：**

- **智能路由**：可以根据 URL 路径、HTTP 头、Cookies 等进行细粒度路由。
- **高级功能**：SSL 终止、内容缓存、压缩、WAF 安全。
- **使用场景**：Web 应用、API 网关、微服务架构。
- **代表产品**：Nginx、HAProxy、AWS ALB、Envoy

::: 详情 它是如何工作的

```
Client request → L7 Load Balancer → Parses HTTP content
                    ↓
          Inspects URL, Header, Cookie
                    ↓
          Intelligent routing to specific server
```

:::

### 2.3 L4 与 L7 比较

|尺寸 |L4 负载均衡 |L7 负载均衡 |
|:--------------------- |:----------------------------- |:--------------------------------------- |
|**OSI层** |传输层（TCP/UDP）|应用层（HTTP/HTTPS）|
|**路由基础**IP地址端口 |URL、头部、Cookie、正文 |
|**处理速度** |极快（内核空间）|快速（用户空间解析）|
|**功能丰富性** |基础转发 |SSL 终止、缓存、压缩、WAF |
|**典型场景**数据库、游戏、长连接 |网页应用、API网关、微服务 |
|**代表性产品** |LVS，AWS NLB |Nginx，HAProxy，AWS ALB |

## 3.核心问题1：防止“损坏”服务器继续服务的方法

### 3.1 健康检查：别让不健康的事件拖累系统

想象一下，你的一个收银台坏了，但分配人员不知道，还不断把顾客送去那里。排队的人越来越长，顾客也越来越愤怒。

**健康检查是防止这种情况的“哨兵”**。他们会定期“检查”每台服务器，立即移除任何“生病”的服务器，并在他们“恢复”后再带回来。

<!-- <健康检查演示 /> -->

### 3.2 主动健康检查与被动健康检查

**主动健康检查**：负载均衡器主动“敲门”，问服务器：“你还在吗？”

- 定期发送探针请求（例如 HTTP /health、TCP ping ）
- 如果响应超时或返回错误代码，则认为服务器不健康
- **优势**：准确可靠的检测
- **缺点**：产生额外的探针流量

**被动健康检查**：负载均衡器“观察”真实业务流量的响应模式

- 跟踪实际请求的响应时间和错误率
- 在多次连续失败后，认为服务器不健康
- **优势**：不产生额外流量
- **劣势**：需要足够的流量样本来做出判断

::: 详细信息 阈值设置
|度量 |健康阈值 |不健康阈值 |注释 |
|:---|:---|:---|:---|
|**HTTP 状态码** |200-399 |400 或超时 |4xx/5xx 均被视为失败 |
|**TCP连接** |成功建立 |连接超时 |检查端口是否可达 |
|**响应时间** |< 500毫秒 | > 2000毫秒 |超时通常设置为2-5秒 |
|**连续失败** |- |3次 |避免瞬态点的假阳性 |
|**检查间隔** |- |5秒 |过频繁会增加负载 |

::: 提示 💡 常见陷阱：阈值设置得过于“敏感”
一个团队将健康检查响应时间阈值设定为100毫秒，但其应用的平均响应时间在80-120毫秒之间波动。因此，服务器经常被标记为“不健康”，导致流量在健康与不健康状态之间波动，整体系统可用性实际上下降。

**正确方法**：阈值应设置为P99响应时间的2-3倍**，留有足够缓冲区以应对正常波动。
:::

## 4.核心问题2：确保回访用户始终获得“后端实例”的方法

### 4.1 会话持久性：让“返回用户”始终找到“后端实例”

想象一下，你是珍珠奶茶店的常客，每次都是同一个员工为你服务。她知道你的喜好（半糖不加冰），而且服务迅速且细致。但如果每次换来新人，你就得一遍又一遍地重复同样的请求——效率会大幅下降。

**会话持久性（粘性会话）**解决了这个问题：确保同一用户的请求总是被路由到同一个后端服务器。

<SessionPersistenceDemo />

### 4.2 三种会话持久机制的比较

|机制 |工作原理 |优点 |缺点 |使用场景 |
|:--------------- |:--------------------------------------------------- |:--------------------------------------- |:------------------------------------------- |:----------------------------- |
|**Cookie插入** |LB在响应中插入Cookie;后续请求携带该Cookie |不受IP变更影响;从第一次请求起持续存在 |客户端必须支持Cookies;可能被禁用 |购物车，登录会话 |
|**IP 哈希** |哈希客户端 IP 并将其映射到特定服务器 |无需客户端支持;无状态 |IP 变更时会话丢失;难以均匀分布 |无 Cookie 环境，WebSocket |
|**粘性会话表**LB维护一个会话与服务器的映射表 |支持会话复制和故障切换 |消耗LB内存;需要额外的同步 |严格高可用性要求的场景 |

::: 提示 💡 使用建议

- **Cookie插入**：首选推荐;最佳兼容性
- **IP 哈希**：仅适用于如 WebSocket 等特殊场景
- **粘贴会话表**：结合Cookie提供故障切换功能
  :::

## 5.核心问题3：实现零停机部署的方法

### 5.1 蓝绿部署：“一键切换”，用于零停机发布

**核心理念**：同时维护两个相同的生产环境（蓝色和绿色），但任何时刻只有一个环境服务实时流量。

<BlueGreenDeploymentDemo />

**工作流程：**

1. **初始状态**：蓝色环境运行v1.0（生产环境），绿色环境待命。
2. **部署新版本**：将v1.1部署到绿色环境并进行内部烟雾测试。
3. **切换流量**：将负载均衡器指向绿色环境;流量即刻切换到v1.1。
4. **监控**：观察绿色环境的行为，确认无异常。
5. **保留旧版本**：将蓝色环境保持在v1.0一段时间（例如24小时）作为快速回滚的安全网。

::: 提示 ✨ 利与弊
|优点 |缺点 |
|:---|:---|
|✅ 零停机时间;切换完成时间为毫秒 |❌高资源消耗;需要维护两个环境 |
|✅ 快速回滚;发现问题请立即切回 |❌数据库模式的变更需要特殊的兼容性处理 |
|✅ 新环境可在接管流量前进行全面测试 |❌不适合有状态服务（例如，WebSocket 长连接） |

:::

### 5.2 金丝雀发布：“小步伐，快速迭代” 金丝雀策略

金丝雀发布的名称来源于历史上的“矿井金丝雀”——矿工会把金丝雀带入矿井；如果金丝雀表现出不适的迹象，就意味着有有毒气体泄漏，矿工会立即撤离。在软件发布中，金丝雀发布意味着首先让一小部分用户接触新版本，观察是否有问题，然后逐步扩大发布范围。

<CanaryReleaseDemo />

**核心思想：**

1. **小流量优先**：最初将 1% 的流量路由到新版本服务器。
2. **观察指标**：持续监控错误率、延迟和关键业务指标。
3. **逐步发布**：如果一切正常，逐步将比例增加到 5%、10%、25%、50% 和 100%。
4. **快速回滚**：如果发现任何异常，立即将所有流量切回旧版本。

::: 提示 💡 金丝雀发布的优势
| 优势 | 描述 |
|:---|:---|
| 🎯 **可控风险** | 即使新版本存在严重漏洞，只有少量用户会受到影响 |
| 📊 **真实环境验证** | 在真实生产环境中验证，比预演环境更可靠 |
| 🚀 **快速迭代** | 团队可以更自信、更频繁地发布新功能 |
| 💰 **节省资源** | 不需要像蓝绿部署那样拥有两个完整环境 |

:::

## 6. 核心问题4：使系统“自动扩展”的方法

### 6.1 自动扩展：让系统灵活调度工作负载

想象一下你经营一家餐厅：

- **午餐高峰**：你需要 10 名服务员，但在下午 3 点的低谷时段，你只需要 2 名
- 如果你始终保持 10 名：人工成本会爆炸
- 如果你始终只保持 2 名：高峰时段的顾客无法等待，都会离开

**自动扩展** 让系统像餐厅一样“灵活调度”——在忙时自动增加服务器，在空闲时自动减少服务器。

<自动缩放演示 />

### 6.2 选择缩放指标

自动扩展的核心问题是：**什么时候应该增加机器？什么时候应该减少它们？**

常用决策指标：

| 指标                     | 扩容阈值           | 缩容阈值             | 使用场景                       |
| :---------------------- | :----------------- | :------------------- | :------------------------------ |
| **CPU 利用率**           | > 70%              | < 30%                | 计算密集型应用                  |
| **内存利用率**           | > 75%              | < 40%                | 内存密集型应用                  |
| **QPS（每秒查询数）**    | > 1000/s           | < 400/s              | API 网关、Web 服务              |
| **连接数**               | > 5000             | < 1000               | 数据库、消息队列                |
| **自定义业务指标**       | 取决于业务         | 取决于业务           | 特定业务场景                    |

::: 提示 💡 扩展策略的陷阱与解决方案

**陷阱 1：扩展响应太慢；流量激增已经导致系统崩溃**

在一次大型电子商务促销期间，团队将 CPU > 80% 设为扩展触发条件，但指标收集有 1 分钟的延迟，而新实例启动需要 3 分钟。流量到达得太快 —— 在扩展完成之前，服务器已经不堪重负。

**解决方案：**

- **主动扩大规模**：根据历史数据预测交通高峰，并提前30分钟开始扩展
- **多层阈值**：设60%为警告（开始预热新实例），70%为正式扩展，80%为紧急扩展
- **快速扩展**：使用容器化部署，使新实例在30秒内启动（而虚拟机需要3-5分钟）

**陷阱2：升级过于激进;成本爆炸性**

一家初创公司制定了激进的自动扩展政策：如果CPU>50%就升级。结果，正常的业务波动触发了扩展，服务器数量从5个暴增到30个。月底的云账单让CTO感到恐惧。

**解决方案：**

- **设定升级冷却时间**：一次升级后，至少等待5分钟后再进行升级
- **设置最大实例数**：max = 当前实例数×2，以防止无限增长
- **区分峰值与趋势**：只有当阈值连续3个周期超过时才会放大，以避免在单点峰值触发

**陷阱3：缩放过快;新加入的机器会立即被移除**

一个团队将CPU设<30%作为缩放触发。缩放后，流量仍在稳定，CPU短暂降至25%，触发缩减。缩放后，CPU又回升至80%，触发了另一轮缩放——系统在“缩放、缩减、缩放”的循环中剧烈波动。

**解决方案：**

- **更保守的缩减**：扩大门槛为70%，缩减阈值为25%，中间留有缓冲
- **缩放冷却时间更长**：缩放后至少等待10分钟再缩放
- **渐进缩减：一次只移除一个实例，观察后决定是否继续
  :::

## 7.实用指南：选择负载均衡器的方法

### 7.1 主流负载均衡器的比较

|功能 |Nginx |HAProxy |Envoy |云服务提供商 LB |
|--------------------- |------------------------------------ |-------------------------- |------------------- |------------------ |
|**定位**高性能反向代理 / LB |开源负载均衡器 |云原生代理 |管理负载均衡器 |
|**性能**极高（C，事件驱动）|高（事件驱动）|高（C /生锈）|极高 |
|**功能丰富度**基础LB，静态文件，缓存 |Rich LB算法 |高级路由，可观测性 |功能丰富 |
|**配置** |配置文件（nginx.conf）|配置文件（haproxy.cfg）|API / 配置文件 |UI控制台 |
|**可扩展性**C模块 / Lua脚本 |Lua脚本 |WASM / 过滤器 |插件 |
|**用例**静态资产，L7 LB，SSL 终止 |L7 LB，高可用性 |服务网格，多云 |快速启动 |

::: 提示 💡 选择指南
**决策树：**

```
Choose a load balancer:
│
├─ Only need basic L4 load balancing?
│  ├─ Yes → LVS (open-source, free) or cloud provider NLB
│  └─ No → Continue
│
├─ Need service mesh or multi-cloud deployment?
│  ├─ Yes → Envoy
│  └─ No → Continue
│
├─ Need extremely complex configuration and plugins?
│  ├─ Yes → HAProxy
│  └─ No → Continue
│
├─ Need high performance + simple configuration?
│  ├─ Yes → Nginx (first choice)
│  └─ Continue
│
├─ Want managed operations?
│  ├─ Yes → Cloud provider LB (AWS ALB, Alibaba Cloud SLB)
│  └─ Self-host Nginx
```

:::

## 8. 总结：负载均衡的核心思维模式

### 8.1 核心原则回顾

| 原则       | 含义                                           | 关键实践要点                                               |
| ---------- | ---------------------------------------------- | ---------------------------------------------------------- |
| **分层**   | L4 处理“包分拣”（快速但简单）                 | 数据库、游戏使用 L4；网页、API 使用 L7                 |
| **冗余**   | 单点故障是敌人                               | 通过多实例、多区域部署提高可用性                          |
| **渐进性** | 不要用“一刀切”的方式发布新版本               | 蓝绿部署实现零停机；灰度发布控制风险                      |
| **弹性**   | 系统应像生物一样“呼吸”                        | 繁忙时自动扩容，空闲时自动缩容                            |

### 8.2 设计检查清单

在引入负载均衡前，问自己以下问题：

- [ ] 是否真的需要负载均衡？（单机性能是否真的不足）
- [ ] 选择 L4 还是 L7？（根据业务场景）
- [ ] 如何处理会话保持？（Cookie、IP 哈希、会话表）
- [ ] 如何实现健康检查？（主动、被动、阈值设置）
- [ ] 如何实现零停机？（蓝绿部署、灰度发布）
- [ ] 如何实现弹性？（扩缩容指标、冷却时间、最大实例数）

## 9. 术语表

| 术语                          | 中文翻译           | 解释                                                                                  |
| ----------------------------- | ----------------- | ------------------------------------------------------------------------------------ |
| **Load Balancer**             | 负载均衡器          | 在多个后端服务器之间分配流量的设备或软件                                               |
| **L4 Load Balancing**         | 四层负载均衡        | 基于传输层（TCP/UDP）的负载均衡                                                      |
| **L7 Load Balancing**         | 七层负载均衡        | 基于应用层（HTTP/HTTPS）的负载均衡                                                   |
| **Health Check**              | 健康检查            | 定期检查后端服务器健康状态的机制                                                      |
| **Session Persistence**       | 会话保持            | 确保来自同一用户的请求总是路由到同一服务器                                           |
| **Sticky Session**            | 粘性会话            | 会话保持的另一种说法                                                                 |
| **Blue-Green 部署**     | 蓝绿部署            | 使用两个环境切换的零停机发布策略                                                    |
| **Canary Release**            | 金丝雀发布          | 先对少量流量进行验证的金丝雀发布策略                                                |
| **Auto Scaling**              | 自动扩缩容          | 根据负载自动增加或减少服务器数量                                                     |
| **Horizontal Scaling**        | 水平扩展            | 通过增加服务器数量来提高处理能力                                                     |
| **Vertical Scaling**          | 垂直扩展            | 升级单台机器的规格（CPU、内存）以提高处理能力                                        |
| **Multi-Region**              | 多区域              | 在多个地理区域部署服务                                                                |
| **Active-Active**             | 多活                | 多个区域同时提供流量服务                                                              |
| **Active-Standby**            | 主备                | 只有一个区域提供流量服务，其他区域处于待机状态                                        |
| **Data Replication**          | 数据同步            | 跨区域的数据复制机制                                                                  |
| **RTO**                       | 恢复时间目标        | 恢复时间目标——系统发生故障后必须恢复的目标时间                                        |
| **RPO**                       | 恢复点目标          | 恢复点目标——系统故障后可接受的数据丢失量                                           |
