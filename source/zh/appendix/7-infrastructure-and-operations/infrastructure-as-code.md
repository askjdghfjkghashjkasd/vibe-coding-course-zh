::: tip 前言
**你是否经历过这样的噩梦：生产服务器宕机，但没人记得它最初是如何配置的？** 手动登录服务器，从记忆中运行命令，祈祷自己不会打错——这就是传统运维的日常现实。基础设施即代码（IaC）彻底改变了这一切：使用代码定义和管理基础设施，使服务器配置像软件一样可版本控制、可复现、可审计。

## 0. 大局观：为什么基础设施也需要“源代码”

想象你是一名厨师。如果你每道菜都凭感觉下盐——今天一勺，明天两勺——味道永远不会一致。但如果你把食谱写下来——明确说明每种调料的克数——任何人都可以复现同样的味道。

基础设施管理同样面临这个问题。单台服务器的配置可能涉及几十个参数：操作系统、网络规则、安全组、存储卷、环境变量等等。手动配置不仅容易出错，还**不可复现、不可审计、不可逆**。

::: tip IaC 的核心价值
- **可复现**：相同代码无论执行多少次都会产生相同结果（幂等性）
- **可版本控制**：通过 Git 管理基础设施变更——谁修改了什么、为什么一目了然
- **可审计**：所有变更都有记录，满足合规要求
- **可自动化**：通过 持续集成 / 持续部署 流水线实现自动部署，消除人为错误
- **协作性**：团队成员通过 Pull Request 审核基础设施变更，就像代码审查一样
:::

## 1. IaC 概念：从“手动点击”到“代码声明”

传统运维是这样的：登录云平台控制台，手动点击创建服务器、配置网络、设置安全组。当管理少量服务器时，这种方法可行，但当扩展到几十甚至数百台服务器时，就会成为噩梦。

IaC 的核心思想是：**使用声明式代码描述你期望的基础设施状态，让工具自动实现**。你无需告诉工具“先创建 VPC，再创建子网，然后创建安全组”（命令式）。相反，你只需说“我想要这样的网络环境”（声明式），工具将自动计算所需步骤。

<IaCConceptDemo />

| 维度 | 手动操作 | 基础设施即代码 |
|------|-----------|----------------|
| 操作方式 | 登录控制台并点击 | 编写代码文件 |
| 可复现性 | 依赖文档和记忆 | 代码就是文档，100% 可复现 |
| 变更跟踪 | 无记录或记录不完整 | Git 版本控制，完整历史 |
| 协作方式 | 口头沟通、文档传递 | Pull Request 审核 |
| 回滚能力 | 手动反向操作 | git revert  重应用 |
| 一致性 | 环境之间差异大 | 开发/测试/生产完全一致 |

::: tip 声明式 vs 命令式
- **声明式**：描述“我想要什么”，工具自动决定“怎样去做”。Terraform 和 CloudFormation 使用这种方法。优点是幂等性好；缺点是灵活性有限。
- **命令式**：描述“如何去做”，逐步执行。Ansible 和 Shell 脚本使用这种方法。优点是灵活；缺点是难以保证幂等性。
- **混合式**：Pulumi 和 AWS CDK 使用通用编程语言编写，将声明式状态管理与命令式灵活性结合。
:::

## 2. Terraform 工作流程：编写 → 计划 → 应用

Terraform 目前是最流行的 IaC 工具，由 HashiCorp 开发。其工作流程清晰且直观，分为四个阶段，类似软件开发中的“编码 → 审核 → 部署 → 清理”。

<TerraformWorkflowDemo />

::: tip 四阶段工作流程
1. **编写**：使用 HCL（HashiCorp 配置语言）编写基础设施定义文件（.tf），声明所需资源：服务器、数据库、网络等。
2. **计划**：运行 `terraform plan`。Terraform 会比较当前状态与期望状态并生成“执行计划”——告诉你打算创建、修改或删除哪些资源。这是一个安全保障，可在实际执行前确认变更。
3. **应用**：确认计划无误后，运行 `terraform apply`。Terraform 会按照计划创建或修改资源。执行后，当前状态保存到状态文件（terraform.tfstate）。
4. **销毁**：当不再需要时，运行 `terraform destroy` 清理所有资源，避免不必要的成本。
:::

| 命令 | 目的 | 是否修改基础设施 | 使用场景 |
|------|------|-----------------|---------|
| `terraform init` | 初始化项目，下载提供者 | 否 | 初次使用或添加新提供者 |
| `terraform plan` | 预览变更，生成执行计划 | 否 | 每次变更前必须运行 |
| `terraform apply` | 执行变更，创建/修改资源 | 是 | 在确认计划后执行 |
| `terraform destroy` | 销毁所有资源 | 是 | 清理测试环境，停用服务 |
| `terraform state` | 查看/管理状态文件 | 取决于操作 | 状态迁移、资源导入 |

## 3. 工具对比：选择合适的 IaC 工具

IaC 领域有多种工具，各有侧重点。选择工具时，需要考虑团队技术栈、云平台及项目规模。没有“最佳”工具——只有最适合你场景的工具。

<IaCToolComparisonDemo />

| 工具 | 语言 | 云支持 | 学习曲线 | 使用场景 |
|------|----------|--------------|---------------|----------|
| Terraform | HCL | 多云 (AWS/Azure/GCP) | 中等 | 多云环境，团队协作 |
| Pulumi | Python/TS/Go | 多云 | 低（熟悉的编程语言） | 开发者友好，适合复杂逻辑 |
| AWS CloudFormation | JSON/YAML | 仅 AWS | 中等 | 纯 AWS 环境 |
| AWS CDK | Python/TS/Java | 仅 AWS | 低 | AWS 编程语言偏好 |
| Ansible | YAML | 多云、裸金属 | 低 | 配置管理，混合环境 |

::: tip 如何选择？
- **初创公司 / 单云**：CloudFormation (AWS) 或该云平台的原生工具，获得最佳生态整合
- **多云 / 中大型团队**：Terraform — 社区最大，提供商最多，招聘最容易
- **开发者主导团队**：Pulumi 或 CDK — 使用熟悉的编程语言编写基础设施，IDE 支持良好
- **需要配置管理**：Ansible — 擅长服务器内部配置（安装软件、修改配置文件）
:::

## 4. 配置漂移：隐形定时炸弹

配置漂移是 IaC 实践中最隐蔽的敌人。它指的是 **实际基础设施状态与代码定义状态之间的逐渐偏离**。

这种漂移通常如何发生？有人为解决生产问题“快速修复”，直接登录控制台手动更改安全组规则。有人为了调试临时增加服务器配置，但忘记恢复。这些“微小的更改”随着时间累积，最终导致代码与实际环境严重不一致。

<ConfigDriftDemo />

::: tip 配置漂移的危险
1. **不可复现**：代码描述的环境与实际环境不一致，创建新环境时会出现问题
2. **回滚失败**：你以为回滚到之前版本可以恢复一切，但实际环境已被人工修改
3. **安全风险**：手动开放端口和放宽权限可能被遗忘，成为攻击入口
4. **审计失败**：合规审计基于代码，但代码无法反映真实状态
:::

| 预防措施 | 描述 |
|-------------------|-------------|
| 禁止手动更改 | 通过 IAM 策略限制控制台操作权限 |
| 定期漂移检测 | 定期运行 `terraform plan` 检查差异 |
| 自动修复 | 在检测到漂移时自动执行 apply 恢复一致性 |
| 变更审计 | 启用 CloudTrail 等审计日志，追踪所有变更来源 |

## 5. 最佳实践：让 IaC 项目可持续

IaC 代码就像应用代码一样，需要良好的工程实践来确保可维护性。随着基础设施规模的扩大，无结构的 IaC 代码会成为另一种“技术债务”。

<IaCBestPracticeDemo />

::: 提示 六大核心最佳实践
1. **模块化**：将可重用的基础设施抽象为模块（如 VPC 模块、数据库模块），避免复制粘贴。就像写函数一样——定义一次，到处调用。
2. **环境隔离**：开发、测试和生产使用独立的状态文件和变量文件，通过工作区或目录结构实现隔离。
3. **远程状态管理**：状态文件（tfstate）存储在远程后端（如 S3 和 DynamoDB），支持团队协作和状态锁定，防止并发冲突。
4. **敏感信息管理**：密码、密钥及其他敏感数据不应写入代码。使用 Vault 或 AWS Secrets Manager 等工具进行管理。
5. **持续集成 / 持续部署 集成**：将 terraform plan 集成到 PR 流程中；apply 通过流水线自动执行，消除本地手动操作。
6. **代码审查**：基础设施变更需要像应用代码一样进行代码审查，尤其是涉及安全组和 IAM 策略的变更。
:::

## 总结

基础设施即代码是现代云原生运维的基石。它将“难以描述的手动操作”转变为“可版本控制的代码”，把基础设施管理从“艺术”变为“工程”。

本章的关键要点：

1. **IaC 的本质**：使用代码声明基础设施的期望状态，让工具自动实现
2. **Terraform 工作流**：写 → 计划 → 应用，三步骤操作，其中 Plan 是安全网
3. **工具选择**：多云 → Terraform，单云 → 原生工具，开发团队 → Pulumi
4. **配置漂移**：最隐蔽的风险，需要通过流程和工具双重保护
5. **工程化管理**：模块化、环境隔离、远程状态和 持续集成 / 持续部署 集成都是必要的
