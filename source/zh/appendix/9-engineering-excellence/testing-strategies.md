# 测试策略导论

::: 提示 前言
**你的代码真的“无bug”吗？**每次代码修改后，你都会手动点击查看是否有故障——这在项目规模小时有效。但当代码库增长到数万行，团队扩展到十几人时，“手动点击”就变成了灾难。

本章帮助你理解软件测试的核心策略，从测试金字塔到TDD，建立系统的质量保证思维。

## 0.大局观：自动化测试的动机

想象你是一名结构工程师。每次蓝图修订后，你不会亲自爬上每一层楼检查结构是否安全——你依赖一个**自动检测系统**。软件测试是代码界的“结构检测系统”。

::: 提示 自动化测试的价值
- **回归保护**：当你修改功能A时，自动检查功能B、C和D是否受到影响
- **信心重构**：有了测试覆盖，你可以自信地重构
- **活文档**：好的测试是最好的使用手册
- **快速反馈**：几秒钟内即可判断代码是否正确，而非部署后才发现问题
:::

## 1.测试金字塔：测试的等级与比例

### 1.1 三层金字塔

迈克·科恩提出的测试金字塔是测试策略的经典模型。它告诉我们：**不同类型的测试应有不同的数量比**。

<测试金字塔演示 />

### 1.2 金字塔形状的动机

金字塔形状反映了一个核心权衡：**速度与真实感之间的平衡**。

- **底层（单元测试）**：极快、数量最多、成本最低，但仅验证单个部件
- **中间层（集成测试）**：适中速度，适量，验证各部件协同工作
- **顶层（端对端测试）**：最接近真实用户，但速度慢，维护成本高，容易发生环境相关故障

> **反模式：冰淇淋锥** — 如果你的项目拥有最多的端对应测试和最少的单元测试，你就有一个倒置的“冰淇淋甜筒”。这意味着你的测试套件运行缓慢，频繁失败，维护成本极高。

## 2.单元测试实践

### 2.1 什么才是好的单元测试

好的单元测试遵循**首先**原则：

| 原则 | 含义 | 描述 |
|------|------|------|
| **F**ast 快速 | 快速 | 在毫秒级内完成；开发者愿意频繁运行 |
| **I**ndependent 独立 | 独立 | 测试彼此不依赖；每个测试可以独立运行 |
| **R**epeatable 可重复 | 可重复 | 在任何环境下得到相同结果 |
| **S**elf-validating 自我验证 | 自我验证 | 明确的通过/失败结果；不需要人工判断 |
| **T**imely 及时 | 及时 | 与代码同时或之前编写 |

### 2.2 测试结构：AAA 模式

每个测试都应具有明确的三部分结构：

```javascript
test('should correctly calculate price with tax', () => {
  // Arrange — set up test data
  const price = 100
  const taxRate = 0.13

  // Act — call the function under test
  const result = calculateTotalWithTax(price, taxRate)

  // Assert — verify the result
  expect(result).toBe(113)
})
```

### 2.3 哪些要测试，哪些不该检查

**应该测试一下：**
- 核心业务逻辑（价格计算、权限检查、数据转换）
- 边缘情况（零、零、负数、极大数）
- 错误处理路径

**无需测试：**
- 第三方库的内部实现
- 简单得分手/二传手
- 框架功能（例如 Vue 的反应系统）

## 3.TDD：测试驱动开发

### 3.1 红绿重构周期

TDD（测试驱动开发）的核心是一个简单的循环：**先写测试，然后写实现，最后重构**。

请使用下方的互动组件，体验完整的TDD周期：

<TDDCycleDemo />

### 3.2 TDD的三大规则

1. **除非让失败的测试通过，否则不要写任何生产代码**
2. **只写足够证明失败的测试**（编译错误算作失败）
3. **只写足够通过测试的生产代码**

### 3.3 TDD的真正价值

TDD的价值超越了“先写测试”——它**迫使你思考界面设计**。当你先写测试时，你会从“用户”的角度思考：这个函数应该接受哪些参数？它应该返回什么？这自然会带来更好的API设计。

提示 TDD 不是万能灵丹
TDD非常适合逻辑密集的代码（算法、业务规则、数据转换），但在UI布局、探索性原型等场景中，强制TDD反而会拖慢你的速度。关键是理解其原则并灵活应用。
:::

## 4.选择测试策略

### 4.1 按项目类型测试重点

|项目类型 |测试重点 |推荐比例 |
|----------|----------|----------|
|**实用工具库 / SDK** |主要单元测试 |90% 单位 10% 集成 |
|**API 服务** |主要集成测试 |30% 单元 60% 集成 10% E2E |
|**网络应用** |均衡分布 |50% 单位 30% 集成 20% E2E |
|**MVP / 原型**关键路径 E2E |少量核心测试就足够了 |

### 4.2 通用测试工具

|工具 |类型 |使用场景 |
|------|------|----------|
|**Vitest** |单元/集成 |Vite 项目的首选;兼容 Jest API |
|**玩笑** |单元/集成 |Node.js生态系统中最受欢迎 |
|**剧作家** |端对端 |跨浏览器;由Microsoft开发 |
|**Cypress** |端对端 |开发体验极佳;调试简便 |
|**测试库** |组件测试 |从用户视角测试 UI 组件 |

## 5.人工智能驱动：利用大型语言模型提升测试效率

LLM在测试领域已经非常有能力——它们可以帮助你生成测试用例，发现边缘案例，甚至编写完整的测试代码。

### 5.1 生成单元测试

> **提示**：
>```
> Please write unit tests for the following function using the Vitest framework:
> 1. Follow the AAA pattern (Arrange-Act-Assert)
> 2. Cover the happy path, edge cases, and error paths
> 3. Each test case should have a clear description
>
> [Paste your function code]
> ```

### 5.2 发现边缘案例

> **提示**：
> ```
> Analyze the following function and list all possible edge cases and
> extreme input scenarios, including: null, zero, negative numbers,
> extremely large numbers, special characters, concurrency situations, etc.
> For each scenario, describe the expected behavior and potential risks.
>
> [Paste your function code]
> ```

### 5.3 从需求生成测试（TDD 辅助）

> **提示**：
> ```
> I want to implement a shopping cart module with these requirements:
> - Add items, remove items, modify quantities
> - Automatically calculate total price (with discounts)
> - Show error when stock is insufficient
>
> Following TDD methodology, first write test cases (no implementation),
> using Vitest, covering all core scenarios.
> ```

::: 提示 AI 使用建议
始终检查 AI 生成的测试断言是否有意义——避免像 `expect(true).toBe(true)` 这样的无用测试。好的测试在代码出错时应该真正失败。
:::

## 6. 总结

1. **测试金字塔**：底层多，顶层少；在速度与真实度之间取得平衡
2. **单元测试**：遵循 FIRST 原则和 AAA 模式；测试核心逻辑
3. **测试驱动开发（TDD）**：红-绿-重构循环；使用测试驱动设计
4. **策略选择**：根据项目类型和阶段选择合适的测试比例

::: 提示 最后思考
测试不是负担——它是**加速器**。短期来看，编写测试确实需要额外时间；长期来看，它节省了无数小时的手动验证、回归缺陷调查和深夜紧急修复。好的测试让你有信心说：**“放心改吧——测试会告诉我们是否有问题。”**
:::

## 进一步阅读

- **经典书籍**：Kent Beck 的《测试驱动开发》是 TDD 的基础著作。
- **实践指南**：尝试使用 Vitest 为一个小项目编写测试，从零体验测试过程。
- **测试模式**：了解 Mock、Stub 和 Spy 的区别及使用场景。
- **持续集成**：将测试集成到 持续集成 / 持续部署 流程中，以便每次提交时自动运行测试。
