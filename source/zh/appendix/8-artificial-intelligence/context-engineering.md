> 💡 **学习指南**：提示工程解决“如何清晰表达”；上下文工程解决“如何让模型在正确的时间看到正确的信息”。本章围绕一个问题：**在有限的上下文窗口内，如何让模型理解你而不超出预算？**

## 0. 引言：会话中途遗忘的动机——以及为什么它越来越贵

<AgentContextFlow />

许多人在使用大语言模型时遇到类似情况：

- 会话中途，模型突然“忘记”之前提到的关键条件；
- 在长对话中，回答互相矛盾，难以保持一致的设置；
- 随着对话回合积累，费用像计程车一样攀升。

直觉上，我们倾向于认为：**“这个模型记性不好。”**
但大部分时候，问题并不是模型“记不住”——而是我们**没有正确设计它可以看到的上下文。**

<IntroProblemReasonSolution />

面对这些挑战，仅依赖“写更好的提示”是不够的。我们需要一种更系统的工程方法，确保模型始终接收最关键的信息——在有限的窗口和预算内。这正是**上下文工程**要解决的问题。

## 1. “上下文工程”概览（定义与场景）

让我们先给出一个简明的工作定义，然后看几个典型场景。

> 上下文工程是一门为大语言模型构建和管理“信息环境”的工程学科。它决定模型“看到什么、忽略什么、以及何时看到”，从而在有限的上下文窗口内实现稳定的任务完成。

简单来说，它归结为三件事：组织信息、控制窗口、管理成本。
常见用例包括：

- 对话代理和客服机器人
- 代码 / 文档助手
- 多轮工具调用与长流程协作

接下来，我们将从一个真实团队的“血泪经验”开始，看看他们如何逐步从“只会写提示”发展到“精通上下文工程”。

## 2. 从“血泪经验”开始：Manus 团队遇到的坑

本章的案例研究来自 **Manus**（一个通用 AI 代理）。
与普通对话不同，Manus 需要自主规划并调用工具来完成长任务（涉及几十甚至上百轮交互）。

这产生了一个核心矛盾：
- **如果你不记住**：关键信息丢失，任务失败。
- **如果你全都记住**：成本和延迟爆炸，可能超出窗口限制。

经过多次架构重构，Manus 团队意识到一个真理：**上下文不能只是“写出来”——必须“设计”。**

### 2.1 四次重构给我们带来的教训

Manus 联合创始人纪宜超分享了他们的“坑历程”:

| 迭代 | 遇到的问题 | 当时的思考 | 结果 |
| :--- | :--- | :--- | :--- |
| **第一次** | AI 在对话中经常忘记 | “只要写更多提示就行” | 提示更长，成本更高 |
| **第二次** | 重要信息总是被挤掉 | “多次复制重要内容” | 文本更长，成本更高 |
| **第三次** | 账单高得让人震惊 | “能否重用之前的计算？” | 找到降低重复计算成本的方法 |
| **第四次** | 长文档无法处理 | “能否仅在需要时查找信息？” | 构建了“按需检索的资料库”方案 |

**核心洞察**：**关键不是记住更多，而是更聪明地记住。**

### 2.2 AI 的“记忆”究竟如何

**传统计算机内存** = **硬盘**：
- 大容量：可以长期存储大量数据；
- 低成本：存储一年相对便宜；
- 读写速度较慢：查找信息需要时间。

**AI 场景下** = **小白板**：
- 读写快：模型可以在一次调用中直接看到整个上下文；
- 空间有限：一旦满了，旧内容必须被抹掉；
- 每写一个 token 都会产生额外计算和成本。

**Manus 的教训**：**要节省且聪明地使用白板——不要用它来存放百科全书。**

## 3. 第一步：了解成本 — 每一分钱的去向

### 3.1 从成本入手的动机

让我们看看在一次典型 AI 对话中你的钱是如何花出去的：

```
💰 Cost Breakdown (per conversation):
├─ 70% re-reading old content ("What did we just talk about?")
├─ 20% processing new content ("What are you saying now?")
└─ 10% generating a reply ("How should I respond?")
```

**惊人的发现**：**70%的费用花在让AI重新阅读你已经说过的内容！**

### 3.2 KV 缓存概览（前缀重用）

在讨论定价之前，我们需要理解一个核心技术概念：**KV 缓存（键值缓存）**。  
别被术语吓到——它本质上是 AI 的“短期记忆备忘单”。

- **没有 KV 缓存**：每次 AI 都必须从第一个字符开始阅读、理解并计算，就像第一次看到文本一样。  
- **有 KV 缓存**：AI 会存储已经处理过部分的计算结果（预填充）。下次如果开头内容没有变化，它会直接检索已缓存的结果，跳过重复计算。

这就像是：  
> 你走进考场。  
> **场景A**：每次你都必须从头到尾阅读整本教科书，然后才能开始作答。（慢、累、贵）  
> **场景B**：你已经记住了教科书内容（缓存），所以坐下就能直接开始作答。（快、轻松、便宜）

在云服务提供商的计费表中，**“缓存命中”的内容（Cache Hit）**通常比**“新内容”（Cache Miss）**便宜 90% 以上。

### 3.3 “记忆”与“按需查询”的价格差异

以 Claude 为例：  
- **按需查询**（无缓存）：$3.00 / 百万 tokens  
- **从记忆中**（有缓存）：$0.30 / 百万 tokens  
- **差距 10 倍！**

**Manus 的实践**：通过让 AI“记住教科书”，将成本从 **$0.15 降到 $0.02** —— **节省 87%**！

### 3.4 陷阱指南：不要让时间戳破坏你的“缓存”

许多开发者习惯性地把“当前时间”放在系统提示（System 提示词）的第一行，以为这样很严格。  
**但这是上下文工程中最大的反模式之一。**

想象一下：你已经记住了一整本历史书（System 提示词），结果第一行显示“当前秒”。  
如果这一行每秒都变化，那么你一秒前记住的所有内容都会失效——你必须从头重新记忆。

这是**前缀重用（KV 缓存）**的阿喀琉斯之踵：**如果开头变化，之后的所有内容都必须重新计算。**

#### 错误的做法：将动态信息放在开头```text
System: The current time is 2024-01-01 12:00:01. You are an assistant...
(One minute later)
System: The current time is 2024-01-01 12:01:01. You are an assistant...
```**后果**：虽然只有少数几个字符发生了变化，但因为它们位于最开始的位置，随后 99% 的固定内容都无法利用缓存重用。每个请求的速度和消耗都和第一次一样慢、一样高。

#### 正确的方法：将静态内容与动态内容分开```text
System: You are an assistant... (thousands of characters of fixed rules and knowledge base go here)
User: (Pass in the current time via a tool call or user message)
```**优势**：成千上万条规则从不改变；AI只需“记住”它们一次。后续请求会直接使用缓存的记忆，使速度快如闪电。

## 4. 第2步：滑动窗口——当“记忆”变成“成本”

随着对话变长，你遇到的第一个问题是：**当窗口已满会发生什么？**

### 4.1 “先进先出”打破的动机

最简单的内存管理是**滑动窗口**：**新内容进来，旧内容出去。**
听起来公平，但在实际任务中，这是一场灾难。

**场景回放**：```text
Conversation log:
[1] User: I'm Zhang San, responsible for the payments system
[2] User: The project uses Go
[3] User: The database is PostgreSQL
...
[20] User: Write an API endpoint for me
```**结果**：当你看到第20条消息时，第1条消息（“我是张三”）已经被推出窗口。AI已经完全忘记你是谁以及你负责什么系统。

**核心问题**：这种策略将**关键信息**（身份、技术栈）和**填充信息**（“好的”、“收到”）视为同等重要——一并被移除。

### 4.2 “中间遗忘”——AI总是错过关键信息的动机

除了“遗忘快”之外，AI还有另一个特点：**它也会‘忽略’某些内容**。  
研究表明：**AI对开头和结尾最敏感，最可能忽略中间部分**。这就是著名的**中间丢失**现象。

**U型记忆曲线**：```text
Position: Start → Middle → End
Memory:   High  →  Low   → High
```

## 5.步骤3：选择性保留——“钉住”关键信息的方法

如果“先进先出”行不通，我们该怎么办？
Manus的回答是：**建立“信息层级”。**

### 5.1 按重要性排序信息的动机

停止对待每条信息一视同仁——根据重要性决定哪些保留，哪些保留：

|层级 |信息类型 |处理 |成本影响 |
|:--- |:--- |:--- |:--- |
|**VIP** |系统设置，用户身份 |**永久保存** |15%成本 |
|**重要** |当前任务目标 |**任务持续时间内保持** |10%成本 |
|**正常** |常规对话记录 |**保持最近5回合**基础成本 |
|**一次性** |可检索知识 |**需要时查找** |-60%成本 |

**核心理念**：**多花25%的钱来保留90%的关键信息。**

### 5.2 “钉住”策略

把上下文窗口想象成一块白板：
- **VIP信息**：**钉在白板最顶端（系统提示）。
- **重要信息**：**磁吸**到白板中间（上下文注入）。
- **普通对话**：写在白板下半部;当空间用尽时，擦掉最早的（滑动窗口）。

## 6.步骤4：RAG — 何时“内存”需要一个“库”

有时候信息量实在太多（比如数百页的技术文档），白板无法全部存储。这时你需要一个外部大脑——**RAG（检索增强生成）**。

### 6.1 为什么“小白板”不够

当Manus面对数百万字的技术文档时，他们比较了两种方法：

1. **完整摄取**：一次性把所有内容塞进上下文中。
    * **后果**：白板瞬间满，处理极慢，根据“迷失中间”理论，AI甚至记不得中间内容。
    * **费用**：~每次请求50美元，等待15秒。
2. **按需检索（RAG）**：先搜索图书馆（数据库），然后只将相关段落复制到白板上。
    * **结果**：白板保持干净;AI专注于关键信息。
    * **费用**：~每次请求0.50美元，等待2秒。

**节省99%的成本和87%的时间节省！**

### 6.2 “查找信息”的最佳实践

马努斯的经历总结如下：
* **每个“页面”应该有多大？** 500-1000字符效果最好。
* **一次要查多少“书”？** 3-5本——越多越多会让人分心。
* **检索前有多重要？** 相似度>0.7，以避免强制删除无关内容。

## 7.第五步：压缩——在“白板”上更密集地书写的方法

如果所有信息都很重要，无法删除，而你又不想查资料怎么办？
那你别无选择，只能**写更小**——这就是**上下文压缩**。

### 7.1 “速记”需求标准
* 检索的材料过厚（>2000字符）。
* 对话历史过于冗长（占白板空间>80%）。
* 你需要快速回答，不想让AI在一大堆文字中摸索。

### 7.2 “速记”的三层次

|压缩方法 |压缩比 |保留了什么 |使用场景 |成本节约 |
|:--- |:--- |:--- |:--- |:--- |
|**摘要** |70% |主要观点 |快速概述 |节省30% |
|**关键点**50% |关键点 |结构化输出 |节省 50% |
|**表格**30% |核心数据 |程序化处理 |保存 70% |

## 8.系统集成：构建AI的“记忆宫殿”

到目前为止，我们已经学到了各种独立的策略，比如构建模块：
* **KV缓存**：帮我们省钱（第三章）
* **滑动窗口**：帮助我们腾出空间（第四章）
* **分级保留**：帮助我们保留重要物品（第五章）
* **RAG**：赋予我们外部智慧（第6章）

现在是时候把这些方块组装成一座完整的城堡——我们称之为马努斯的**“记忆宫殿”。**

### 8.1 组装上下文，比如建造房屋

不要把上下文看作一堆杂乱无章的文字;把它想象成一栋层叠叠的建筑。每一层都有其独特的功能和“居住规则”。

### 8.2 这个设计如此强大的动机

这座宫殿的设计理念旨在解决三个矛盾：

1. **基础（系统提示）——解决“昂贵”问题**
    * **矛盾**：系统设置（你是谁，规则是什么）是最长的部分，每次都必须发送。
    * **解决方案**：将其置于底层。利用**KV缓存**技术，只要不变，AI可以“从记忆中背诵”。数百轮后续对话中，该部分的计算成本接近**$0**。

2. **支柱（任务上下文）——解决“遗忘”问题**
    * **矛盾**：随着对话时间增加，AI很容易忘记最初的任务目标（例如，“写一个蛇类游戏”）。
    * **解决方案**：使用**分级保留**策略将任务目标“钉在第二层”。无论对话多少轮，这一层永远不会被删除，确保AI永远不会忘记原始目标。

3. **顶层（聊天与RAG）——解决“混乱”问题**
    * **矛盾**：有新的对话和检索到的参考资料——将它们混在一起会造成混淆。
    * **解决方案**：
        * **客厅（聊天）**：通过**滑动窗口**管理，只保留最新的5-10条热消息。
        * **图书馆（RAG）**：参考资料时有有，从不占用永久空间。

### 8.3 真实世界成绩

Manus团队部署该架构后，效果立竿见影：

*   **节省成本**：由于基础被“记住”，每轮对话成本下降了 **84%**。
*   **速度提升**：AI 不再每次都从零读取数千字符；平均响应时间从 8 秒下降到 **2 秒**。
*   **准确性提升**：关键信息被“固定” — AI 在对话过程中不会忘记其应执行的任务。

### 📝 即用实战设计

如果你正在设计一个像 Manus 这样的系统，不要只关注如何编写提示，更要关注 **系统架构如何协调上下文**。

以下是两个经典场景的 **系统设计蓝图**，包含 **提示设计** 和 **代码逻辑（伪代码）**。

#### 场景 1：全栈工程师代理（长期记忆型）
> **核心挑战**：长期任务周期容易忘记原始需求和项目上下文。
> **策略**：系统层（身份）   任务层（固定目标）   聊天层（滑动窗口）。

**1. 系统提示（第 1 & 2 层）**```markdown
# Layer 1: Identity Setup (System Prompt) - Never changes, leverages KV Cache
You are a senior full-stack engineer, proficient in Python and Vue3.
Coding style:
- Variable naming strictly follows PEP8
- Critical logic must include comments
- Prioritize existing project utility functions

# Layer 2: Task Pinning (Task Context) - Must not be deleted during the task
Current task: Refactor payment module (payment_module)
Core constraints:
1. Must maintain compatibility with legacy API v1.0
2. Database migration scripts must be idempotent
3. Deadline: This Friday
```

**2. 上下文组装逻辑（伪代码）**```python
def build_engineer_context(user_input, chat_history, task_info):
    context = []

    # 1. Foundation layer: Identity setup (leverages KV Cache)
    # This part doesn't change for hundreds of rounds; computation cost is near $0
    context.append(SYSTEM_PROMPT)

    # 2. Pillar layer: Task pinning (Pinned)
    # No matter how long the conversation, this is always inserted after System
    context.append(f"Current task: {task_info}")

    # 3. Retrieval layer: Code snippets (RAG)
    # Search the codebase for relevant code based on the user's question
    relevant_code = search_codebase(user_input)
    if relevant_code:
        context.append(f"Reference code:\n{relevant_code}")

    # 4. Interaction layer: Conversation history (Sliding Window)
    # Only take the last 10 turns to avoid blowing up the context
    recent_chat = chat_history[-10:]
    context.extend(recent_chat)

    # 5. Latest input
    context.append(user_input)

    return context
```

#### 场景 2：智能客服代理（精准问答型）
> **核心挑战**：成本敏感，绝对不能虚构答案。
> **策略**：系统层（强约束）   RAG 层（动态注入）。

**1. 系统提示（第一层）**```markdown
# Layer 1: Identity Setup (System Prompt)
You are a professional e-commerce customer service representative.
Response principles:
1. A warm, professional, and concise tone
2. **Absolutely prohibited** from fabricating facts; only answer based on [Reference Materials]
3. If the materials don't contain an answer, respond directly with "I'm very sorry, I'll need to transfer you to a human agent for this question"
```

**2. 上下文组装逻辑（伪代码）**```python
def build_support_context(user_input):
    context = []

    # 1. Foundation layer: Identity setup
    context.append(SYSTEM_PROMPT)

    # 2. Library layer: Dynamic retrieval (RAG)
    # Only in customer service scenarios does RAG take center stage, placed in the middle
    docs = vector_db.search(user_input, top_k=3)

    context.append("【Reference Materials Start】")
    for doc in docs:
        context.append(doc.content)
    context.append("【Reference Materials End】")

    # 3. Interaction layer: Very short history
    # Customer service typically doesn't need long memory; keep the last 3 turns
    context.extend(get_recent_chat(limit=3))

    context.append(user_input)

    return context
```

## 10. 术语表

| 英文术语 | 中文翻译 | 解释 |
| :--- | :--- | :--- |
| **上下文窗口** | 上下文窗口 | 模型在单次处理过程中可以处理的最大文本长度（包括输入和输出）。超出此限制的内容将被截断或遗忘。 |
| **词元** | 词元 | LLM 处理的最小文本单位。大约 1 个词元 ≈ 0.75 个英文单词或 0.5 个中文字符。计费和窗口限制都以词元为单位。 |
| **KV Cache** | KV 缓存 | 一种推理加速技术，通过缓存已计算的注意力键值对，避免对重复前缀的冗余计算，从而显著降低延迟和成本。 |
| **RAG** | 检索增强生成 | 在回答问题之前，从外部知识库检索相关信息并提供给模型作为上下文，减少幻觉并扩展知识边界。 |
| **Sliding Window** | 滑动窗口 | 最基本的上下文管理策略。保持窗口内的词元数量恒定；当新内容进入时，最早的旧内容会自动移除。 |
| **Lost in Middle** | 中间迷失 | 大模型的局限性。研究显示，模型对长上下文的开始和结尾信息记忆最佳，而容易忽略中间的信息。 |
| **System 提示词** | 系统提示 | 放在对话开头的指令，用于设置模型的身份、行为规范、回答风格和核心任务。 |
| **Few-shot** | 少样本学习 | 在提示中提供几个“问答”示例，帮助模型快速理解任务模式和输出格式。 |
| **Chain of Thought** | 思维链 | 引导模型在给出最终答案前输出推理步骤。这种方法显著提升模型解决复杂逻辑和数学问题的能力。 |
| **幻觉** | 幻觉 | 模型自信地生成看似合理但实际上错误或不存在的信息的现象。 |
| **向量嵌入** | 向量化 | 将文本转换为高维数值向量的技术。语义相似的文本在向量空间中更接近，是语义搜索的基础。 |
| **Vector DB** | 向量数据库 | 专门用于存储和检索向量数据的数据库。支持相似度搜索，以快速找到与查询最匹配的文档片段。 |
| **Temperature** | 温度 | 控制模型输出随机性的超参数。较高值（如 0.8）产生更多样化和创造性的输出；较低值（如 0.2）产生更确定性和精确的输出。 |
| **TTFT** | 首字延迟 | Time to First 词元 —— 用户发送请求到模型输出第一个词元所经过的时间。衡量交互体验的重要指标。 |

## 总结：上下文工程的精髓

Manus 的四次重构教会我们：

**从实用角度**看：关键不在于记忆更多，而在于以更有结构和选择性的方式记忆。

**从成本角度看**：
- 大部分浪费来自于对固定前缀的冗余计算，必须通过前缀稳定性和缓存机制来解决;
- 重要信息被错误丢弃往往源于“一刀切”的滑动窗口，必须通过信息分层和钉定策略来解决;
- 面对极其庞大的文档和知识库时，仅依赖扩展上下文窗口是不现实的——必须结合检索和压缩机制。

目标是：在给定的模型和上下文限制内，确保每个投资的代币都有明确的用途。
